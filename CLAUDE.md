Silver speculative-positioning monitor with gold as comparative context. Framing is **"selling dollars, not buying metals"** — is the speculative futures crowd genuinely capitulated, or just pulling back. ## Standing architectural rules (apply to every tab below)

- **Persist-on-fetch**: every route that talks to an upstream source has a `_fetch_and_persist_*` function that fetches, reshapes, and writes to SQLite; a paired `/db`-suffixed route reads the same data straight back out with no upstream call. **The frontend calls only `/db`-suffixed (or `/api/cot/db`, `/api/prices/db`) routes — it never triggers a live upstream fetch itself.** Rationale: CATCOR's and Delivery Behavior's cross-check features assume AV's database is already the real record, not a pass-through — a route that fetched live on every request would let two simultaneous reads observe two different upstream states, breaking that assumption. (Formerly documented in the retired `SPEC.MD`'s "Persist-on-Fetch Re-architecture" section — see the note on `SPEC.MD` above; this is now the canonical statement of the rule.) **Sanctioned exception, encoded as `ALLOWED_NON_DB_API` in `tests/test_conventions.py`**: user-initiated refresh *commands* (Money Supply's Refresh button → `/api/fred/money-supply/refresh` + `/api/metals/prices/refresh`, the Data tab's Re-run now → `POST /api/health/refresh/{key}`, `POST /api/refresh/force`, `/api/catcor/refresh`). These trigger a `_fetch_and_persist_*` server-side; the frontend still only ever *reads* `/db` routes afterward — the rule's real content is that no data-read path fetches upstream, not that no user action may trigger a persist.
- **One shared database**: `runtime/argentvigil.db` (gitignored), owned by `backend/db.py`, `DB_PATH` computed `__file__`-relative (two directories up from `backend/db.py`, into `runtime/`). Every tab's tables live here — there is no per-tab or per-layer database file. `runtime/` contains nothing else (an earlier flat-file cache for CATCOR's ForexFactory feed was migrated into a table — see CATCOR section below).
- **Backend package layout**: `backend/` is a real package (`backend/__init__.py`, empty, enables `from . import db` and `uvicorn backend.main:app`). `seed_data/` (manually-maintained static content) and `runtime/` (gitignored generated state) are namespace packages / non-packages sitting alongside it, not nested inside it.
- **Tiered background refresh, per-source cadence** (`main.py`'s `lifespan`/`_schedule_loop`): a single generic scheduler dispatches every registered source per its own `CadenceSpec`, without the frontend ever calling upstream. **Fast tier** = spot prices only (the one genuinely intraday-moving figure, one shared tunable `fast_interval_s`). **Slow tier** = every other `trigger="interval"` source — as of the per-source-cadence pass, each one owns its own real `interval_seconds` reflecting its own upstream cadence, not one shared blanket interval: `EXCHANGE_INVENTORY_INTERVAL_S` (~25h — a day plus a safety margin) for the 14 daily exchange-inventory sources (COMEX/SHFE inventory, delivery notices, leverage, PSLV, curve spread); weekly for `money_supply` and `census_trade` (the latter's own `min_gap`-based self-gating inside its fetch_fn still enforces the true ~25-day floor regardless of how often the scheduler ticks); daily for `metals_prices`; monthly for `treasury_outlays`/`treasury_outlays_by_agency`. **`lbma_fix` is the one exception, deliberately not on this list** — briefly given the same `EXCHANGE_INVENTORY_INTERVAL_S` recurring cadence during the per-source-cadence pass, then reverted to plain `manual_only` (no `fire_at_startup` either) days later after that recurring version burned through GoldAPI.io's free-tier 500 req/month quota — the original per-cycle cost estimate (2 req/fetch) missed that the fetch function's own "today not posted yet" fallback can double it to 4 req/cycle, and this data has no frontend consumer to justify continuous polling of a quota-scarce source in the first place. See the Silver/Gold sections' LBMA fix entry below for the full detail; re-evaluate a recurring cadence only if this data gets a real UI surface again. Both tiers run once, unconditionally, at server startup (`fire_at_startup=True`), then **default to enabled** (flipped from disabled-by-default in the per-source-cadence pass, since a continuously-run instance should track upstream on its own rather than go stale between manual force-refreshes) — the enabled flag persists across restarts via `ui_settings.refresh_enabled` (`db.set_refresh_enabled`/`get_refresh_enabled`, same single-row-upsert convention as the pinned-default-tab feature; previously in-memory-only, silently reverting to the hardcoded default on every restart). `POST /api/refresh/force` runs both tiers once immediately regardless of enabled state, returns real per-tier `{"succeeded","failed","errors"}` counts, and — only if at least one source actually succeeded — dispatches a `FORCE_REFRESH_EVENT` window `CustomEvent` that Inventory/CoT/CATCOR panels listen for to re-read their `/db` data immediately. CoT and Research are excluded from force-update (CoT stays pipeline-only; Research is on-demand chat, nothing to force-refresh). `frontend/src/refresh_controls.jsx`'s `RefreshControls` panel (re-mounted in the Data tab as of this pass, previously built but unrendered) exposes fast tier's enable+interval and slow tier's enable-only toggle (no shared slow interval to expose anymore) plus the force-update button; per-source cadence is hand-tuned via the Data tab's existing per-source interval override (`POST /api/data-sources/{key}/interval`), not from this panel.
- **Nulls over zeros**: subsumed into the "Never manufacture a reading" convention — see ## Cross-cutting data conventions directly below. Per-tab references to "the nulls-over-zeros convention" all point there now.
- **Stale spot feed over weekends/closures**: `/api/prices`'s underlying `twelvedata-ws` feed doesn't pause when COMEX/LBMA silver/gold trading is actually closed — confirmed live over a weekend that it kept returning a top-level `isStale: true` flag (sibling of `data`, not per-metal) alongside a `cacheAge` in the hours, while still stamping each entry with a live-looking `timestamp` and slowly drifting the price via rounding/re-sampling jitter on metalcharts.org's own end. `_fetch_and_persist_prices` (`main.py`) checks `isStale` **and** `date.today().weekday() >= 5` (real Sat/Sun) before skipping persistence — no new `spot_price` row is written on a real weekend, so a chart reading it goes flat at the last real print instead of showing fake weekend movement that never actually traded. On a weekday, `isStale=true` is persisted anyway rather than skipped — confirmed live that `isStale` can also fire on a weekday with `cacheAge` in the **months** (metalcharts.org's own upstream feed stuck, not a market closure); skipping indefinitely in that case would silently flatline the chart forever with no visible signal anything's wrong, so a stuck weekday feed is deliberately allowed to surface directly in the chart instead. Apply the same check to any other route that reads `/api/prices`' response.
- **The Data tab MUST be updated whenever app data changes — this is a strict requirement, not a nice-to-have.** As of datasources-spec.md's Story #1 split, this now spans two homes by kind of change: operational metadata (cadence, rate limit, `requires_env`, table ownership, affinity group) lives in **`backend/sources.py`** — any new/changed source's fetch cadence or rate-limit posture must land a matching `SourceDefinition`/`CadenceSpec`/`RateLimitSpec` edit there; editorial prose (per-field descriptions, curl examples, origin text) stays hand-written in **`frontend/src/data_editorial.json`** (`data_editorial.js` is now a thin re-export wrapper — edit the JSON, never the wrapper; JSON specifically so `tests/test_conventions.py`'s registry↔editorial sync guard can consume the same file Python-side, and that guard *fails the suite* when a registered source has no editorial card, making this rule mechanically enforced rather than remembered). `frontend/src/data_panel.jsx` renders both halves, joined by `sourceKeys`. Any change that adds/removes/renames a SQLite table or column, adds/removes/changes an upstream source or its fetch shape, or changes a source's fetch cadence/rate-limit posture must land a matching edit to the relevant one (or both) of these files in the same change. Treat a data-shape change without a Data-tab update as incomplete, the same as a migration without a schema update.
- **This doc's own per-tab sections must be updated in the same change as any user-visible feature addition, not just the Data tab's registry/editorial pairing.** The rule above is mechanically enforced (`test_conventions.py` fails the suite on a registry↔editorial mismatch); this one isn't — prose content isn't practically assertable the way a registry key's presence is — so it has to be followed by discipline, not a test. A new sub-panel, chart, or tab section reaching main with a correct `SourceDefinition`/editorial card but no corresponding "## Tab: X" prose is exactly the kind of drift a future session can't detect by reading code alone (this happened for real: Money Supply grew from 4 documented sub-panels to 9 shipped ones — Federal Outlays, Outlays by Agency, Treasury Auctions, and Foreign Holdings of U.S. Treasuries all landed with correct registry entries and zero doc mention, caught only by a full audit). Treat a doc update as part of the same change as the feature, same weight as the version-bump convention in Development Notes.
- **Pinned default tab**: a 📌 icon on each of `App.jsx`'s six nav buttons lets the user designate which tab opens by default on load, instead of always defaulting to CoT. Persisted server-side (`ui_settings` table, single-row upsert — same convention as `pipeline_runs` — via `GET`/`POST /api/ui/pinned-section`), **not** `localStorage` (the app has no client-only persistence anywhere; a shared setting like this belongs in the same SQLite database as everything else). `App.jsx` fetches the pinned section on mount and opens it if valid; falls back to `"cot"` if nothing's pinned or the fetch fails. `ui_settings` also carries `refresh_enabled` as of the per-source-cadence pass (see Tiered background refresh above) — same single-row-upsert shape, one more column on the same settings row rather than a new table.

## Cross-cutting data conventions

Canonical statements of the data-handling rules that recur across tabs. Each began life as a single-tab decision and quietly became a de-facto convention; consolidated here 2026-07-20 and **deliberately re-ratified by the user rather than just transcribed** (every entry below was reviewed as "is this actually the rule I want" — they are). Per-tab sections say "per the X convention" and point here instead of restating; the test suite (see TODO) guards these mechanically.

- **Never manufacture a reading ("numbers or nothing")** — the umbrella rule; "nulls over zeros" is its oldest special case. The original assertion: *"if I manufacture data, I tell an inaccurate story."* AV never persists or renders a fabricated number. Concretely: (a) upstream zero-sentinels meaning "not reported" become `NULL` at persist time (`_parse_aggregate_row` in `main.py` — metalcharts.org's `0`s); (b) a computed value whose inputs are missing is `NULL`, never `0` (`curve_spread_pct` when either leg has no real price); (c) forward-fill may bridge an *interior* gap between two real readings (needed for consistent baselines when comparing weekly/monthly/intraday cadences on one chart, and for Recharts stacked-area geometry) but is always capped at that series' own last real date — a fill never extends a series past its real coverage (`money_supply.jsx`'s `lastRealM2Date`/`lastRealWalclDate` caps, and the per-series caps in `mergeComposition`); (d) a number confirmed unreliable is persisted as `NULL`, not left in place for a future reader to trust (`volume_oi`/`gold_volume_oi.open_interest` post-CFTC-only fix). Charts gap; readouts show "—"; bridging between two known numbers is acceptable, guessing beyond them never is.
- **Nearest-date matching — three named variants; new code picks one by name.** All three are intentional; historically they were chosen per-feature without seeing the family, so the variants are pinned here. A fourth variant needs a documented reason, not just precedent. (1) **As-of lookup** — strictly on-or-before: "what was X's value as of date D." Used by the leverage backfill's registered-inventory join, `VaultSnapshotPanel`'s pinned-date reads, the Composition pie's Wednesday snap. (2) **Pin-snap** — on-or-before, falling back to nearest-after only when the pin predates that chart's entire dataset. UI-only: snaps a shared `pinnedDate` onto each chart's own date grid before drawing a `ReferenceLine` (Recharts category axes need an exact `x=` match). Canonical implementation: `nearestRowDate` in `frontend/src/date_utils.js` — a shared module as of this consolidation, previously duplicated verbatim in `money_supply.jsx` and `silver_cot_tracker.jsx`. (3) **Tolerance join** — nearest within ±N days, either direction: merging two series with genuinely different date grids; N comes from the two series' real cadences, chosen per pair (±3 days leverage↔curve-spread, ±1 day volume — `nearestBy` in `silver_cot_tracker.jsx`; `nearestGsr`'s CoT↔GSR pairing is the same move).
- **Staleness threshold is 2× expected interval.** A source is stale when time since last success exceeds `2 × expected_interval_s` — one missed cycle can be timing jitter; two consecutive misses means something is actually wrong. Computed client-side in `computeStatus` (`data_panel.jsx`, exported and shared by `App.jsx`'s `HeaderHealthDot`, `health_context.jsx`'s `HealthProvider`/`useHealthRows`, and `chart_staleness.jsx`'s `ChartStaleness`) against the per-row threshold `GET /api/health/db` ships; the backend derives the threshold from `CadenceSpec` but never computes status itself (one computer of status, one shipper of thresholds — see Tab: Data). The 2× multiplier predates this section and lived only in frontend code; ratified as the deliberate rule when consolidated here. **Per-sub-panel staleness badges** (`ChartStaleness`, added in the per-source-cadence pass): every tab's collapsible sub-panels — CoT's 4, Money Supply's 8, Inventory's 6-ish across `comex_inventory.jsx`, CATCOR's 1 — render this same status (a colored dot, relative age via `timeAgo`, a "Refresh now" button hitting `POST /api/health/refresh/{source_key}`) in their own `<summary>` row, not just on the Data tab. A sub-panel backed by more than one source_key (e.g. a chart merging leverage + curve spread data) shows the worst status across all of them — one badge per chart, not one per underlying source, per this convention's own default. `health_context.jsx`'s `HealthProvider` polls `/api/health/db` once (60s, same cadence `HeaderHealthDot` always used) and every badge across every tab reads from that single shared poll via `useHealthRows`, rather than each sub-panel polling independently — a real N-independent-polls problem this avoids by construction once badges spread across this many sub-panels. Market Demand/Demand Composition (Inventory tab, static seed data, no live upstream) and Research (on-demand chat, nothing to be stale) have no badge — there's no source_health row for either to point at.
- **Derived values are computed at read time, never persisted.** Persist only what upstream actually said; anything derivable from persisted data is recomputed on each read, so a formula fix is a code change, never a data migration. Instances: `/api/cot/db`'s percentiles/track-record/GSR, `expected_interval_s` (derived from `CadenceSpec`, stored nowhere), `census_trade`'s `implied_qty_oz` (computed in `db.get_census_trade` — see Tab: Data), market-balance runway derivations, `/api/health/db`'s `tier`, `GlobalSilverPanel`'s tracked-total ratio. **Grandfathered exception**: `net_long_pct_oi` is persisted into `cot_silver`/`cot_gold` by the pipeline — flagged as tech debt (see TODO), not a precedent to copy.
- **Append-only vs. upsert — decided by one question: does the upstream revise published data?** Never revises (CFTC reports, real price ticks) → `INSERT OR IGNORE`, append-only, a published row is never overwritten (`cot_*`, `spot_price`, `forexfactory_calendar`). Revises or re-labels (Census's annual April revisions, LBMA/Yahoo re-fetches, curve-spread re-ranking) → upsert (`census_trade`, `settlement_price`, `futures_curve_spread`). App/infra state → single-row or current-state upsert (`pipeline_runs`, `ui_settings`, `source_health`, `interval_overrides`). **Flagged future consideration, not built**: for official/government sources, an upsert silently discards the pre-revision value, and *when official numbers drift* is itself information the user cares about (drift in unofficial free feeds — Yahoo, metalcharts.org — is expected and trivial). If revision visibility ever becomes a feature, ALFRED already provides point-in-time vintages for the FRED series; see TODO.
- **Unit constants — one canonical list**: COMEX silver contract = 5,000 troy oz; COMEX gold contract = 100 troy oz; 1 kg = 32.1507 troy oz (SHFE); ForexFactory `"K"`-suffixed forecasts scale ÷1000 to PAYEMS's native thousands; FRED per-series unit divisors (WRESBAL/WSHOTSL/WSHOMCB/WLCFLPCL report in **millions**, RRPONTSYD/M2SL in **billions** — never assume a shared divisor, that exact assumption was a real bug). Canonical home: **`backend/units.py`** (`SILVER_CONTRACT_OZ`, `GOLD_CONTRACT_OZ`, `TROY_OZ_PER_KG` — stdlib-free constants only, safe to import from `db.py`/pipeline-side code without the venv). Every backend literal was replaced with these imports as of this consolidation — desync is now impossible by construction; the test suite asserts each value exactly once against this module. Frontend display prose (e.g. `comex_inventory.jsx`'s "÷1000 × 32.1507" caption, `data_editorial.js` field notes) may still state the numbers as human-readable text — those are descriptions, not math; any frontend *computation* needing a conversion factor should receive already-converted values from a `/db` route rather than duplicating the constant in JS.
- **Price instrument registry** — as of `price-architecture-spec.md` (2026-07-20), every Ag/Au price series lives in one of two tables, `spot_price` (tick-resolution, append-only) or `settlement_price` (daily-or-coarser, upsert), keyed by `instrument` (and `settlement_price` additionally by `session`). `instrument` is a **closed set defined once** in `backend/price_instruments.py` — never a bare string literal — replacing the old informal "series_id family" convention that relied on a prose comment to avoid collisions (the exact bug behind CATCOR's futures/spot sawtooth: `spot_price_tick`'s old `"XAG"`/`"XAG_FUTURES"` keys collided before this enum existed). Adding a new instrument means adding one line to `price_instruments.py` in the same change. `fred_observations` still exists, but only for real FRED-native series (`M2SL`, `WALCL`, `CPIAUCSL`, `WRESBAL`, `RRPONTSYD`, `WSHOTSL`, `WSHOMCB`, `WLCFLPCL`) — no price data lives there anymore.

No unified market-calendar/holiday layer exists; if one is ever built, these three converge on it rather than each growing its own.

## Tab: CoT

**Frontend**: `frontend/src/silver_cot_tracker.jsx`. **Backend**: `pipeline/` (fetch + compute) + `backend/main.py`'s `/api/cot/db` route + `backend/delivery_behavior.py`'s category-composition compute (see below — this content is CoT-derived, not Stock & Flow, so it lives in this tab despite being part of the Delivery Behavior module).

### CoT: what it does

Fetches CFTC Commitment of Traders data for COMEX Silver (084691) and COMEX Gold (088691), computes a normalized positioning metric (`net_long_pct_oi` = (non-commercial longs − non-commercial shorts) ÷ total open interest × 100), and ranks it against rolling 2-year and 5-year historical windows. Normalizing by OI makes readings from 2011 and 2024 directly comparable.

**Signal zones** (configurable in `pipeline/config.py`): ≥90th percentile → specs crowded long (caution); ≤10th percentile → specs capitulated (back-up-the-truck zone); between → normal range, no signal. Both windows computed side-by-side; the UI flags disagreement explicitly.

### Panel contents (top to bottom)

The outer panel is titled **"Paper Games"** (renamed from "Positioning Extremes / Speculative Crowding" at the user's request — the App.jsx nav tab itself reads "Trading," a separate rename; this is the in-panel title, same distinction Money Supply already draws between its nav label and its own in-panel "Dollars and Sense" title). It is a **plain, non-collapsible header** (`<div className="comex-panel">`/`comex-panel-header`, not a `<details>`) — changed from collapsible specifically because a collapsible wrapper would let the panel-wide date selector (see below) get hidden along with everything it controls, the same reasoning that already drove Money Supply's own collapsible→plain-header fix. `StalenessLabel` still renders inline in the header.

- **Panel-wide date-range selector** (`PAPER_GAMES_WINDOWS`: 1M/6M/1Y/All + Custom, default 6M, lives in the "Paper Games" header) — drives every historical chart in the panel: `CombinedChart` (in its own nested collapsible "CoT Positioning & Gold/Silver Ratio" sub-panel, see below) and both Silver/Gold sections' `MetalLeverageCurveVolumeChart`. Deliberately **no 1W/2W presets** — COT positioning is weekly data, so a 1-2 week window would show at most 1-2 real points; a user who needs that granularity uses Custom instead (explicit user decision). **Custom** reveals From/To date inputs (same pattern as Money Supply's own Custom range) — client-side only, no fetch is re-triggered; `SilverCoTTracker` computes one shared `{since, until}` pair (`Date` objects or `null`) from either the active preset or the custom bounds and passes it down as props to all chart components, replacing what used to be each chart's own independent `days`-based `useState`. None of `/api/curve-spread/db`, `/api/*/db/leverage/history`, or `/api/cot/db` accept a window/date query param — every chart already fetches its full series once and filters client-side, so this restructure needed no backend changes.

### CoT: data flow

`pipeline/run.py` → parses CFTC rows (via `pipeline/fetch.py`, stdlib-only Socrata client) → persists append-only to `cot_silver`/`cot_gold` (`INSERT OR IGNORE` keyed by `report_date` — a published report is never overwritten) + upserts `settlement_price` (via `pipeline/price_fetch.py`, Yahoo Finance, under the `SLV_CLOSE`/`GLD_CLOSE`/`SI=F_WEEKLY`/`GC_F_WEEKLY` instruments — see the Price instrument registry entry under Cross-cutting data conventions; this used to be a dedicated `cot_prices` table) → stamps `pipeline_runs` (single-row, `id=1`) with completion time, unconditionally, even if no new CoT rows landed → also writes `pipeline/cache/cot_data.json` unchanged (standalone-CLI usability only; frontend never reads it). Persistence goes through `from backend import db` (shared `backend/db.py`, itself pure `sqlite3`/`os`/`contextlib`, no `fastapi`/`httpx`, so importing it doesn't need the venv) — `pipeline/` no longer owns a separate database file.

`GET /api/cot/db` reads `cot_silver`/`cot_gold`/`settlement_price` directly via `db.get_silver_series`/`get_gold_series`/`get_price_series` and recomputes percentiles/track-record/GSR server-side on each request (cheap, ~1,560 rows/metal) using `pipeline/compute.py`'s `compute_from_series`/`compute_signal_track_record` (`compute_from_series` is an additive twin of `parse_and_compute` that takes already-normalized SQLite rows instead of raw CFTC rows). **`/api/cot/db` never triggers a live Socrata fetch** — CoT refresh stays external (`python3 pipeline/run.py`, manual or cron), a deliberate asymmetry from every other tab's `/refresh`+`/db` pattern, since a 15-year Socrata pull is too slow to trigger from an HTTP request. `POST /api/refresh/force` does not touch CoT or `pipeline_runs` either.

As of the Data Health work (see Data tab below), `cot_pipeline` also has its own registry entry (`_refresh_cot_pipeline` in `main.py`) — a rate-limit gate (skips, `last_attempt_status="skipped"`, if the latest persisted report is under 7 days old) wrapping `asyncio.to_thread(pipeline_run.run_pipeline_once)`. This is the first in-app trigger CoT has ever had, reachable via the Data tab's per-source "Re-run now" button; it does not change the fact that `/api/cot/db` itself stays read-only.

### Squeeze Context (`squeeze-context-spec.md`)

Pairs COT positioning extremity with a futures curve spread, plus a small hand-maintained historical case log — "was the specs crowd genuinely stretched, or is this just the front-vs-next-month curve shape," each series carrying its own explicit as-of date, never implied simultaneity. Not a composite score, not an alerting system, not a new tab. Grew out of a conversation about the January 2026 silver spike (>$120/oz), where curve backwardation and stretched Managed Money positioning both preceded the move.

- **Futures curve spread** (`futures_curve_spread` table, `main.py`'s `_fetch_and_persist_curve_spread`, slow tier, `GET /api/curve-spread/db?metal=`) — front-month vs. next-month COMEX settlement spread, both metals, daily. `curve_spread_pct = (next_month_price - front_month_price) / front_month_price`; positive = contango, negative = backwardation; NULL (not 0) on any day either leg has no real price. Sourced from Yahoo Finance's chart API against real deferred-month contract symbols (e.g. `SIU26.CMX`). Yahoo's chart API has no published quota/rate-limit headers; an isolated 429 seen early in development turned out to be a transient/IP-cooldown artifact, not a query-shape or symbol-type block (confirmed via repeat testing, consistent with this endpoint's other call sites in this codebase never hitting one) — `_fetch_and_persist_curve_spread` still does a single retry with short backoff on 429/5xx as defensive margin, not because a real recurring lockout exists.
  - **Front/next-month resolution is liquidity-ranked PER HISTORICAL DATE, not once for "today" and backfilled.** COMEX's real near-term liquidity does not track the textbook active-delivery-month cycle (e.g. a "textbook active" month can trade single-digit volume while a later month carries thousands) — a hand-maintained active-months list was tried first and abandoned once this was confirmed; any future work needing "which contract month is currently liquid" should re-derive it live, never trust a static list. `_candidate_contract_symbols` sweeps both directions from today (`CURVE_SPREAD_CANDIDATE_MONTHS_AHEAD`=8, `CURVE_SPREAD_CANDIDATE_MONTHS_BEHIND`=14) so every symbol that could have genuinely been front/next at any date in the fetch window is a ranking candidate, not just symbols visible from today's vantage point. Front/next must additionally respect delivery order (`_delivery_sort_key`, parsed from the symbol) — "next" is the highest-volume REMAINING candidate whose delivery month is strictly later than front's, not just the second-highest by volume regardless of month order (pure per-date volume ranking without this check can pair an about-to-expire contract against a newer front month and mislabel the chronologically earlier one "next," producing a spurious negative spread that's a backwards pairing, not real backwardation). With both the per-date ranking and the delivery-order check in place, real data across the full trailing year never goes negative — range is roughly +0.6% to +4.6%, tightest during the January 2026 squeeze itself and widest for the widest month-gap pair encountered. Treated as a real finding, not a remaining bug: the front/next paper spread specifically didn't show backwardation during that squeeze, suggesting physical stress concentrated more at spot-vs-front-month than between two already-deferred paper contracts (see the spot-vs-front-month gap noted below, not yet built).
- **Display**: originally a standalone `CurveSpreadPanel` component (`silver_cot_tracker.jsx`) — a current-value badge (front/next symbols, spread %, contango/backwardation label, its own as-of date, always window-independent) plus its own history chart. **Deleted along with the rest of the old component set** during the Silver rebuild/Gold parity work (see the Silver/Gold sections bullet above under Panel contents) — the current-value badge is gone entirely (no frontend surface for front/next symbols or the contango/backwardation label as of this consolidation), and the history chart's curve-spread line lives on inside `MetalLeverageCurveVolumeChart` instead (blue line, right axis, `curve_spread_pct`), sharing that chart's `since`/`until` props from the "Paper Games" panel-wide selector rather than owning independent window state. `GET /api/curve-spread/db?metal=` is unaffected — still the read route `MetalLeverageCurveVolumeChart` fetches from. UI copy standardizes on "curve spread"/"front-month spread," never "the curve" alone (spec's terminology rule — "the curve" is reserved for a true multi-month curve-shape visualization, not built in this pass).
- **Paper leverage vs. curve spread combined chart** — originally shipped as a standalone `LeverageCurveSpreadChart` component (dual-axis line chart, `paper_leverage` left axis vs. `curve_spread_pct` right axis) sitting below `CurveSpreadPanel` in each metal's section. Both were superseded by `MetalLeverageCurveVolumeChart` (see the Silver/Gold sections bullet above under Panel contents) during the Silver rebuild/Gold parity work — the combined chart's pairing logic described below is still exactly how `MetalLeverageCurveVolumeChart` merges these two series today, just under the newer component name and now with volume bars added as a third series on the same chart. **Explicitly not a new derived metric** — `paper_leverage` is TOTAL COMEX open interest across every listed contract month ÷ registered inventory, not scoped to the front-month contract specifically the way curve spread is; a true front-month-only OI/physical ratio would need CME's real per-contract-month OI breakdown, confirmed as a paid Market Data Platform product and permanently out of scope (same gap `delivery_behavior.py`'s `contract_month_oi` gap documents under Tab: Inventory). This chart pairs two real, independently-computed AV series for visual comparison, it does not manufacture a ratio AV has no free path to compute. Merges on curve spread's own dates via **nearest-date matching within 3 days** (not exact-date) — confirmed live that only ~70 of 290 real curve-spread dates had an exact same-calendar-day `paper_leverage` match (the two series' underlying update cadences don't land on the same days very often), so exact-date joining produced a badly gapped leverage line; nearest-date matching (same pattern `CombinedChart`'s `nearestGsr` already uses for pairing CoT against GSR) brought real coverage to 289/290 dates.
- **Combined CoT chart window selector**: `CombinedChart`'s originally-hardcoded 5-year view is now driven by the "Paper Games" panel-wide selector (see Panel contents above) — not its own window buttons, and not the intermediate `COMBINED_CHART_WINDOWS`/per-section-selector design that preceded the final panel-wide consolidation. Client-side filtering of the already-fetched series either way, never a per-window refetch. "All" reaches back to COT's real coverage start (2011-07-12), not an arbitrary large number. Added specifically so curve spread (which only accumulates forward from whenever this feature was deployed) and COT positioning (2011+) can be meaningfully viewed together across different depths of history.
- **Historical case log** (`squeeze_case_log` table, `GET /api/squeeze-cases/db`) — a small, hand-maintained SQLite table of known squeeze/dislocation cases for pattern reference, not a workflow (explicitly not using the Research tab's session/promote/dismiss lifecycle — "it's numbers fetched from an API that we do math on," too heavy for flat reference data). Seeded with 3 bootstrap cases: 2011 Silver Blow-off, 2020 COVID Gold Liquidity Crisis (a documented negative-ish control — liquidity panic, not a positioning squeeze, explicitly not conflated with the other two), and January 2026 Silver Squeeze (the feature's origin case). `curve_reading_snapshot` is nullable and left NULL for all three bootstrap rows — curve spread backfill for cases predating `futures_curve_spread`'s own ingestion start is best-effort, not guaranteed, per the spec. **DB + backend route only this pass — no frontend list/table yet** (see known gaps below).

## Tab: Money Supply

**Frontend**: `frontend/src/money_supply.jsx` (imported directly into `App.jsx`, not nested under another panel). **Backend**: `main.py`'s FRED routes.

### Money Supply: what it does

Tracks the supply of the thing being debased, plus the broader federal-fiscal picture (spending, borrowing, who's funding it), as monetary context for the metals panels.

**Panel structure — two levels of nesting, not three**: the panel header reads **"Dollars and Sense"** (renamed from "Money Supply" at the user's request — the App.jsx nav tab itself is still labeled "Money Supply," this rename is scoped to the in-panel title only) — a plain, **non-collapsible** `<div className="comex-panel">` header, not its own `<details>` (an earlier version wrapped it in a collapsible outer level too and was flattened after the user flagged the extra nesting). Inside it, **nine** independently-collapsible sub-panels are the *only* collapsible level (each its own `<details className="collapsible-pane" open>`, same pattern as Inventory's nested Delivery Behavior panel), in render order: **M2 Money Stock / Fed Balance Sheet**, **Fed Balance Sheet Composition**, **Federal Outlays**, **QE / QT**, **Treasury Yields**, **Treasury Auctions**, **Foreign Holdings of U.S. Treasuries**, **Dollars vs Silver vs Gold as Purchasing Power** — all default open. The window/Custom-range/Refresh controls live in the (non-collapsible) "Dollars and Sense" header, not inside any one sub-panel, since they drive the shared `window_` state across every sub-panel that uses it — nesting them inside a collapsible sub-panel would hide them for the others whenever that one sub-panel was collapsed.

Each collapsed sub-panel's `<summary>` surfaces a compact supplementary-data line so collapsing doesn't hide the headline numbers (e.g. M2's summary shows M2 in trillions + Fed Balance Sheet as % of M2; Composition's shows the current Assets:Liabilities ratio; QE/QT's shows the Assets total + latest weekly change, green/red by sign; TIC's shows the as-of date, Grand Total, and current top-holding country). The M2 sub-panel's stale-data warning includes the actual last-known values, not just how old they are ("M2 last reported 2026-05-01 ($23.1T) ...").

**Standing rule, applied to every summary/pie/tooltip in this tab**: when a date is pinned (see Cross-chart pin below), a sub-panel's summary/pie/tooltip reflects that pinned date's values, not "latest" — each computes its own row via that chart's pin-snap variable when `pinnedDate` is set, falling back to the true latest-real-reading logic only when nothing's pinned. Priority is **pin > hover > latest** everywhere a pie or tooltip has to pick one date, so clicking elsewhere to set a pin is never silently overridden by wherever the mouse happens to be. The M2 sub-panel's stale-data warning is suppressed while a date is pinned, since "stale" describes the true latest reading, not whatever historical date is currently pinned.

**Time window**: 2Y/5Y/10Y/20Y preset buttons (2Y default) plus a **Custom** button revealing From/To date inputs — doesn't fetch until both bounds are set and `start <= end`. `GET /api/fred/money-supply/db` and `GET /api/metals/prices/db` both accept `window`, and — only when `window=custom` — `start`/`end`; `start` becomes the SQL `since` bound, `end` trims the already-fetched rows in Python. The custom-range branch fetches 2 extra years before `start` (same margin the preset branches use) so `_compute_yoy` always has the trailing 12 months it needs — a custom range starting exactly at data coverage's start date will still show YoY from the earliest date a full trailing year exists, not `null` throughout (a real early bug: the first cut set `fetch_since = start` with zero lookback margin, silently `null`-ing every YoY value in any custom range).

**Cross-chart pin (click-to-highlight)**: clicking a point on M2/WALCL, Composition, QE/QT, Yields, Auctions, or TIC sets a shared `pinnedDate`. Clearing is a click on the 📌 pinned-date button in the panel header (right-click-to-clear was tried first and dropped — Safari intercepts `contextmenu` unreliably). The Purchasing Power chart doesn't originate a pin via click, since its mousedown/mouseup are already claimed by its own press-and-hold "since that date" comparison gesture, but still displays a pin set elsewhere. Because each chart has its own date grid (monthly-anchored, weekly-anchored, monthly-resampled) that rarely shares exact date strings with the others, and Recharts' category-axis `ReferenceLine` only renders when its `x=` exists verbatim in that chart's own dataset, every chart snaps the shared `pinnedDate` to its own nearest real row date on/before it (`nearestRowDate`, `frontend/src/date_utils.js`) before drawing the line — pin-snap is the "Pin-snap" variant of the Cross-cutting nearest-date-matching convention.

**Pinned tooltips**: when a date is pinned, each chart also renders a fixed tooltip box directly below it, rather than floating over the `ReferenceLine` (would require synthesizing Recharts' internal per-chart pixel math for a purely cosmetic gain). Each chart's tooltip content lives in its own named component (`MoneySupplyTooltip`, `CompositionTooltipContent`, `QeQtTooltipContent`, `YieldsTooltipContent`, `AuctionMixTooltipContent`, `OutlaysTooltipContent`, `TicHoldingsTooltipContent`, `MetalsTooltip`) called identically by the real hover-driven `<Tooltip content={...}>` and by the pinned box (`active` forced `true`, `label` set to the snapped pinned date) — one source of truth, two triggers.

- **M2 Money Stock / Fed Balance Sheet** — trillions USD, stacked area chart (left axis) + M2 YoY % (right axis). M2's full area (green) is the total money stock; WALCL is shaded **red as the share of that same area it takes up** (`walcl_share` drawn first/bottom, `m2_remainder` = M2 minus that stacked on top, both from `mergeSeries`) — "roughly a third of the green area is red" reads directly off the chart rather than requiring a two-line comparison. Legend (`M2_LEGEND_SERIES`, horizontal, click-to-reveal `eli5`) follows the tab's standard legend convention (see Cross-cutting note below). Both `walcl_share`/`m2_remainder` and the raw M2/WALCL series are forward-filled for stacked-area geometry (Recharts' `stackId` math doesn't interpolate across nulls the way a plain line does, and M2's own real cadence — 1st of month only — is much sparser than WALCL's weekly one), but every forward-fill is capped at that series' own true last real date (`lastRealM2Date`/`lastRealWalclDate`) — a fill never extends past real coverage, per the standing nulls-over-zeros convention. The raw, non-forward-filled `m2` field stays separate for the YoY line/tooltip, which correctly show "—" on days M2 didn't actually report.
- **Fed Balance Sheet Composition** (`specs/fed-balance-spec.md`) — a look inside WALCL's top-line number: all 5 of FRED's H.4.1 candidate series, split into **Assets** (WSHOTSL Treasuries, WSHOMCB MBS, WLCFLPCL Discount Window — these roughly but not exactly track WALCL, since AV doesn't track every WALCL line item) and **Liabilities** (WRESBAL Bank Reserves; RRPONTSYD Reverse Repo, balance-sheet-adjacent but not itself an `"Assets:"` series) per FRED's own series metadata — summing all 5 into one flat total double-counts assets against liabilities (a real early bug: confirmed live giving ~$13.75T against WALCL's real $8.73T the same week). Three view modes (Assets+Liabilities default, Assets Total, Liabilities Total) as two independent stacked-area `stackId`s, never merged. A fixed pie below the chart shows the composition breakdown for whichever date is hovered/pinned/latest, snapped to the nearest Wednesday reading on/before it (RRPONTSYD is daily; the other four are weekly-as-of-Wednesday) — `requiredKeys` deliberately excludes RRPONTSYD from the "every series must be present" gate, since it has a genuine ~9-month gap of no real FRED data (2006-07-19 through 2007-04-26) that would otherwise blank the whole lookup even though the other liability series has real data there. `assetsLiabilitiesRatio = totalAssets / totalLiabilities` plots as a dashed right-axis line, deliberately unclamped (can swing to a large multiple when Liabilities is near zero — a real reading, not a display bug), shown in the summary as `Assets / Liabilities: {ratio}:1`, green above 1.25 / red at or below. Colors are group-coded (Liabilities reddish, Assets greenish, each series its own shade within the family). Confirmed real, not a data-quality issue: the week of 2023-03-15 shows a genuine WLCFLPCL/WRESBAL spike — the SVB/Signature Bank collapse and the Fed's Bank Term Funding Program response, both landing the same week.
- **Federal Outlays** (`fed-spend-spec.md`) — monthly federal Outlays/Receipts/Deficit/Interest-on-debt from Treasury's Monthly Treasury Statement, plus a fiscal-year rollup (`aggregateAnnual`/`fiscalYearOf`). Topline vs. By-Department/Agency toggle: the agency view uses `topAgenciesByLatestMonth` to pick the top 8 departments by their most recent month's spend + an "Other" bucket, ranked once (not re-ranked per period) so a department's color/legend slot stays stable over time — same reasoning TIC's country ordering uses below. Both stacked-area views hit the same stable-slot-index rendering fix TIC's chart uses (Recharts tracks stack position by React key at mount time, not current render order). Backed by two separate registered sources — `treasury_outlays` (topline) and `treasury_outlays_by_agency` (department breakdown) — reading `fiscaldata.treasury.gov`'s Monthly Treasury Statement, each with its own table and `data_editorial.json` card.
- **QE / QT** — bar chart of week-over-week change in the Assets total (billions USD, not trillions — real weekly changes are usually $1B–$150B, below trillions-scale rounding precision, so this is computed directly in billions rather than reusing the trillions-scale field), green if assets grew that week ("QE") / red if they shrank ("QT") via per-`Cell` coloring, diffed against the prior row that actually has a `totalAssets` reading (most rows are RRPONTSYD-only daily rows with nothing to diff). Also carries `totalAssets` itself on a second right axis (trillions, dashed) so level and week-over-week momentum are visible together. Legend (`QE_QT_LEGEND_SERIES`) follows the standard convention; its "Weekly Change" swatch uses a two-tone gradient (half green, half red) since that series has no single color.
- **Treasury Yields** — 7 real FRED series, daily, flat multi-line chart (no grouping/pie — a simpler shape than Composition since these are ungrouped % series sharing one axis): `DGS3MO`, `DGS2`, `DGS5`, `DGS10`, `DGS30`, `DFII10` (10-Year real/TIPS yield), `T10Y2Y` (FRED's own maintained spread, fetched directly rather than computed client-side to avoid rounding drift), plus a client-computed `T10Y3MO` spread. Same FRED fetch machinery as M2/WALCL/CPI (`money_supply` source, `fred_observations` table) — not a new source. `DFII10`'s `eli5` calls out that it's the series most commonly cited as gold's actual opportunity-cost driver (gold pays no yield, so real rates are the textbook mechanism), more so than either nominal yield alone. `mergeYields` is a plain date-key merge (all 7 series share the same real daily cadence — no forward-fill/ratio math needed).
- **Treasury Auctions** — bid-to-cover ratio by security type (Bill/Note/Bond/TIPS/FRN, `mergeAuctionsByType`) plus a buyer-category %-stack mix chart (Primary Dealers/Indirect Bidders/Direct Bidders/SOMA). Backed by `treasury_auctions` (Treasury's Auctions Query API, rolling 120-day window), own table + editorial card.
- **Foreign Holdings of U.S. Treasuries (TIC)** — stacked area of the 14 largest foreign holders (Japan, China, United Kingdom, Belgium, Cayman Islands, Luxembourg, Canada, Total Caribbean, Taiwan, Ireland, Switzerland, Hong Kong, India, Turkey — `TIC_COUNTRY_ORDER`, ranked by real holdings size and deliberately **not** re-ranked per period so each country keeps a stable color/legend slot) plus a Grand Total, from FRED's `FORLTTREASPOS*` series family — long-term Treasuries only, excludes T-bills, so it is **not comparable to Treasury's own separately-published bills-inclusive Major Foreign Holders total**. "Cayman Islands" is a real subset of "Total Caribbean," not a duplicate — summing both double-counts. Rides the existing `money_supply` `SourceDefinition`/`fred_observations` table, no new registration (already has its own dedicated table entry in the `fred` editorial card). Companion pie beside the chart (pin > hover > latest, click a slice to highlight). **Deviates from every other sub-panel's legend convention**: checkbox-per-country show/hide plus click-to-highlight, but **no eli5 click-reveal text** — a real, deliberate gap worth knowing about if this panel's legend is ever touched, not an oversight to silently "fix" without checking first.
  - **Real ~2-month publication lag, confirmed live, not an AV staleness bug** — TIC's own upstream data (Treasury's real reporting cadence, mirrored by FRED) is published roughly two months in arrears, the same structural lag `census_trade` already has (see Tab: Data's Census section). Confirmed directly against FRED's live API on 2026-08-19: `FORLTTREASPOS99996`'s newest real observation was `2026-06-01` — no newer print existed anywhere upstream at that moment, so a panel showing "as of June" on August 19 is correctly caught up, not behind. `money_supply`'s own fetch succeeds on its normal weekly cadence regardless (confirmed via `/api/health/db` — `last_attempt_status: "success"`, no error), since a successful *fetch* only means AV asked FRED and got an answer; it says nothing about how fresh FRED's own answer is. Never treat this panel's as-of date lagging ~2 months behind today's date as a health-check or fetch-cadence problem — check FRED's own most-recent observation for that series before assuming AV is behind.
- **Dollars vs Silver vs Gold as Purchasing Power** — four series (Fiat $100 nominal / Gold XAU / Silver XAG month-end closes since 2006 / CPI-derived Purchasing Power) as relative return % against a user-selected baseline. Click a legend label to set baseline (Purchasing Power can't be baseline — not a holdable asset); checkbox toggles visibility. Click-and-hold a chart point shows "since that date to latest" return in the tooltip (green/red vs. baseline) without redrawing the lines. Keeps its own distinct legend interaction model (checkbox + baseline-select, not click-to-reveal-eli5) since clicking here already does something load-bearing — re-running the real rebase math — at the user's explicit request to keep that mechanism rather than converting it to match the other legends.

**Legend convention across this tab**: every sub-panel except Purchasing Power (functional baseline-select, see above) and TIC (checkbox, no eli5 — see above) uses the same horizontal, click-to-reveal-`eli5` legend (`M2_LEGEND_SERIES`/`COMPOSITION_SERIES`/`QE_QT_LEGEND_SERIES`/`YIELDS_LEGEND_SERIES`/`OUTLAYS_LEGEND_SERIES`-shaped arrays: `legendLabel` for the compact row, `eli5` for the click-revealed full explanation, `dashed` for a dashed-swatch entry) — clicking a row shows/hides its explanation below the legend and highlights that series on the chart (thicker stroke + dimmed others for lines, outlined + dimmed `<Cell>`s for pies/bars).

### Money Supply: data flow

`GET /api/fred/money-supply/refresh` fetches every FRED series this tab uses (M2SL/WALCL/CPIAUCSL, the 5 H.4.1 Composition series, the 7 Treasury Yields series, the 14 TIC country series + Grand Total) and upserts them all into `fred_observations` (generic `(series_id, date, value)` store — also holds Yahoo-sourced metal closes, see below). `GET /api/fred/money-supply/db?window=2y|5y|10y|20y` reads it back, computes YoY + CPI-derived purchasing-power index + TIC trillions-conversion server-side. Requires `FRED_API_KEY`; `refresh` raises a clean `500` if unset. Federal Outlays, Outlays by Agency, and Treasury Auctions are each a separate registered source (`treasury_outlays`, `treasury_outlays_by_agency`, `treasury_auctions`) reading Treasury's own APIs directly, not FRED — each with its own table, route, and `data_editorial.json` card.

**Unit note**: FRED's H.4.1/TIC series do not all share a native unit — WRESBAL/WSHOTSL/WSHOMCB/WLCFLPCL/the TIC country series report in **millions** (same convention as WALCL), RRPONTSYD/M2SL report in **billions**. `/api/fred/money-supply/db` converts each with its own correct divisor (`_millions_to_trillions`) — never assume a shared divisor across FRED series, per the canonical unit-constants convention (Cross-cutting data conventions above).

**Metal price history** (for the purchasing-power chart): `/api/metals/prices/refresh` fetches daily closes from Yahoo Finance via `backend/yahoo_prices.py`, persists into `settlement_price` under the `XAG_YAHOO_DAILY_CLOSE`/`XAU_YAHOO_DAILY_CLOSE` instruments (see the Price instrument registry entry under Cross-cutting data conventions). `/api/metals/prices/db?window=...` resamples to one row per calendar month at read time (last trading day on/before month-end) and returns raw price + index-to-100-at-window-start; the frontend does its own further client-side rebasing against the selected baseline.

### Sanctions Timeline (`sanctionsTimeline-spec.md`)

An overlay, not a new sub-panel: vertical event markers for OFAC sanctions designations, drawn on top of this tab's existing debasement-side charts (M2/WALCL, Fed Balance Sheet Composition, Foreign Holdings of U.S. Treasuries) so sanctions activity can be visually correlated against what the debasement data was doing at the time — nothing more. No scoring, no severity, no aggregation into an index; hover shows entity name/program tag(s)/date, nothing else. The spec's own header lists "owner tab: CATCOR," but that's nominal only — a designation isn't a claim requiring judgment (Treasury already decided it happened), so this deliberately does **not** route through CATCOR's Research Pane promote/dismiss/discard lifecycle; it's closer to a straight data feed. See the one-line pointer under Tab: CATCOR below.

- **Ingestion** (`backend/main.py`'s `_fetch_and_persist_ofac_designations`, registered as `ofac_sanctions`, `affinity_group="gov_regulatory"`, slow tier, `trigger="interval"` ~daily `fire_at_startup=True`, no self-gating — OFAC's bulk download has no published rate limit or key requirement, unlike `census_trade`'s min_gap-gated pattern) — pulls Treasury's OFAC Sanctions List Service **Advanced XML variants**, `sdn_advanced.xml` and `cons_advanced.xml` (confirmed live: `https://sanctionslistservice.ofac.treas.gov/api/download/{filename}`, both 302→signed-S3, ~126MB SDN Advanced / ~4.5MB Consolidated Advanced, no auth, but a **`User-Agent` header is required** — a bare request 403s without one), every day, across **every** OFAC program with no filter at fetch time (Iran, Russia, Venezuela, DPRK, narcotics, cyber, everything) — program-level narrowing is a display/query-time concern against the full stored dataset, never an ingestion-time exclusion, per the spec's explicit scope decision. **Not the plain `sdn.xml`/`consolidated.xml` files** — see the designation_date bullet below for why the Advanced variants are required, and for a real correction to this doc's own earlier claim.
- **Advanced XML is a genuinely different, more normalized schema** than the plain files, confirmed live: three top-level sections — `ReferenceValueSets` (small ID→label lookup dictionaries: `DetailReferenceValues`, `PartySubTypeValues`, `SanctionsProgramValues`, etc.), `DistinctParties` (one `<DistinctParty>`/`<Profile>` per entity — identity/name, entity type via `PartySubTypeID`, vessel-specific `Feature`/`FeatureVersion` detail), and `SanctionsEntries` (one `<SanctionsEntry>` per list-membership — `EntryEvent`/`Date` designation date, `SanctionsMeasure` program tags) — joined by `ProfileID`/`FixedRef` (confirmed live these are the same numeric ID across all three uses for a given entity, e.g. real vessel MAR AZUL is `FixedRef=4238`/`Profile ID=4238`/`SanctionsEntry ProfileID=4238`). Also confirmed live: `sdn_advanced.xml` alone already contains `SanctionsEntry` rows for 4 different `ListID`s (SDN, Consolidated, Sectoral Sanctions, Non-SDN Palestinian Legislative Council), and `cons_advanced.xml` is genuinely NOT redundant with it despite that overlap — 388 of its 481 distinct `ProfileID`s don't appear in `sdn_advanced.xml` at all — so both files are fetched and merged (`_fetch_and_persist_ofac_designations`), later-file-wins on a duplicate `ofac_uid` (93 real overlapping profiles confirmed live, same underlying entity either way). `backend/main.py`'s `_parse_ofac_advanced_xml`/`_ofac_parse_distinct_parties`/`_ofac_parse_sanctions_entries`/`_ofac_parse_reference_dicts` do this parse/join; a real 403-silent-empty-parse bug was caught during implementation (see the entity_type bullet below) and a real namespace bug (Advanced files use a `.../exports/ADVANCED_XML` namespace, NOT the plain files' `.../exports/XML` — confirmed live against a real fetched file's own root element; using the wrong namespace makes every ElementTree lookup silently match zero elements rather than error, so this was caught only by inspecting parsed output against real data, not by a stack trace).
- **`entity_type` resolution needed a real fix mid-build**: `PartySubTypeID` values 1/2 map unambiguously to vessel/aircraft, but 3/4 (Individual/Entity) are BOTH labeled `"Unknown"` in `PartySubTypeValues` — an early version defaulted anything not 1/2 to `"entity"`, which silently misclassified every real Individual as an Entity. Fixed by resolving 3/4 through a second lookup, that `PartySubType`'s own `PartyTypeID` attribute (`PartySubType ID="3" PartyTypeID="2"` → Entity, `ID="4" PartyTypeID="1"` → Individual, confirmed against `PartyTypeValues`' own `ID=1 "Individual"`/`ID=2 "Entity"` labels) — confirmed live post-fix against the real full SDN Advanced pull: 9,918 entity / 7,514 individual / 1,540 vessel / 342 aircraft, a sane real distribution.
- **Diff, not a snapshot dump**: only the *delta* against the prior day's pull is persisted — `db.diff_and_persist_ofac_designations` keys on OFAC's own stable `ofac_uid` (never name matching; OFAC entries carry many aliases/transliterations that get reformatted between publications without the underlying entity changing). A `uid` not seen before → new row. A `uid` seen before and still present → `last_seen_snapshot_date` bumps, **plus a one-time backfill** of `designation_date`/`entity_name`/`program_tags`/`vessel_flag`/`vessel_type` from today's pull whenever the persisted value is NULL/empty (see the designation_date bullet below for why this exists — it converges existing rows toward "every row has its real data" without becoming ongoing content-diffing: a field that's already real is never overwritten by a later pull). A `uid` seen before and now absent → `delisted_date` set on the *existing* row (a state change, never a new row, never a deletion). A `uid` that reappears after being delisted clears `delisted_date` again — the spec is silent on this case; treating a relisting as equivalent to a fresh new listing was the more honest read than leaving a stale `delisted_date` on a currently-listed entity (a documented decision, not inferred from the spec).
- **`designation_date` — a real correction to this doc's own earlier claim.** The plain `sdn.xml`/`consolidated.xml` files genuinely have no per-entity designation-date field (confirmed live 2026-08-25 — only a document-level `Publish_Date` and unrelated per-entity dates like date of birth), which is why this feature originally shipped persisting `designation_date` as permanently NULL. That conclusion was corrected 2026-08-26, after the user pushed back on an empty-looking chart and a re-investigation found the **Advanced** file variants (`sdn_advanced.xml`/`cons_advanced.xml`) DO carry a real one: `SanctionsEntry/EntryEvent/Date`, filtered to `EntryEventTypeID="1"` (`"Created"` per `EntryEventTypeValues` — the only `EntryEventType` value that exists in this data at all) — confirmed live on real entries back to **1981-01-07** through the current date, e.g. MAR AZUL's real designation date is 1989-01-05. A profile with more than one `SanctionsEntry` (multiple lists) keeps the EARLIEST real Created date across all of them. `GET /api/ofac/db`'s response carries a computed `chart_date` field (`COALESCE(designation_date, first_seen_snapshot_date)`, `db.get_ofac_designations`) so the frontend always has a usable anchor even for the rare row without a real date — still never backfilling `designation_date` itself from a fallback, per the standing nulls-over-zeros convention; `chart_date` is the display convenience, `designation_date` stays an honest NULL when genuinely absent.
- **Table**: `ofac_designations` (`ofac_uid` PK/join-key — `Profile/@ID` under the Advanced parse, `entity_name`, `entity_type` [individual/entity/vessel/aircraft — captured now even though the frontend renders one marker type for all types at launch, so a future marker-type breakout is a display filter against data already there, not new ingestion], `program_tags` JSON array stored as TEXT — no existing JSON-array column convention elsewhere in this schema, so `json.dumps`/`json.loads` at the `db.py` boundary; sourced from `SanctionsMeasure` elements with `SanctionsTypeID="1"` ("Program" per `SanctionsTypeValues`) whose own `Comment` element carries the program name directly, confirmed live e.g. `<Comment>CUBA</Comment>` — NOT a separate ID-linked table the way the plain files' `<program>` elements are), `list_source` (`SDN`/`Consolidated` — confirmed live these are genuinely separate lists, not a superset/subset naming quirk), `vessel_flag`/`vessel_type` (nullable, vessel-only — confirmed live against a real vessel entry, e.g. tug MAR AZUL uid 4238; sourced from `Feature`/`FeatureVersion` matched by `FeatureTypeID`, whose own `VersionDetail` value is EITHER inline text OR a `DetailReferenceID` pointer needing a lookup, confirmed live e.g. `DetailReferenceID=705` → `"Tug"`), `first_seen_snapshot_date`, `last_seen_snapshot_date`, `delisted_date`.
- **No overlay display on this tab** — the original vertical-`ReferenceLine`-overlay display on `money_supply.jsx`'s M2/WALCL, Composition, and TIC charts (grouped-by-`chart_date` markers, a checkbox toggle, a click-to-inspect box) was built, then removed at the user's explicit request 2026-08-26 ("I hate the overlays... remove them, they're noise") — not because of the freeze bug (see below, already fixed by the time this was pulled) but a pure display-taste call. `money_supply.jsx`'s rendering of the data was deleted entirely (the `markersInRange` helper, all three chart call sites, the toggle, the detail box); `frontend/src/palette.js`'s `OFAC_MARKER_COLOR` constant was removed alongside it since nothing referenced it anymore. The data itself is not homeless, though — see **Tab: OFAC** below, a standalone nav tab added the same day at the user's own request ("I just want to monitor the list... another tab?") once the overlay idea was scrapped. Ingestion (this subsection, above) is shared by both — `ofac_sanctions`/`GET /api/ofac/db` were never touched by either the removal or the new tab.
- **A real freeze bug was caught and fixed before the removal above**: the first shipped display version rendered one `<ReferenceLine>` per designation (not grouped), and — before a separate `designation_date` fix (see above) — every one of the ~19,700 bootstrap-pull entities shared the single `first_seen_snapshot_date` value that existed at the time, so each of the three charts tried to mount ~19,700 real SVG DOM nodes, recomputed unmemoized on every render (hover/click/pin), which froze the tab within seconds. Was fixed by (a) grouping markers by unique chart date, (b) memoizing per-chart marker arrays via `useMemo`, and (c) a hard render cap as a backstop — worth knowing if a future display revisit reintroduces per-chart marker rendering: don't reintroduce one-DOM-node-per-entity without re-deriving this same grouping.
- **Day-one bootstrap flood** (still relevant to the data, not just the now-removed display): the very first daily pull has no prior snapshot to diff against, so it registers the *entire* current list (~19,700 entities confirmed live) as "new" in one run — an expected one-time event, not a data bug, and not an actual single-day sanctions wave. Real `designation_date` values (see above) mean this flood does NOT collapse onto one date — confirmed live: **1,470 distinct real dates** across the full persisted set, spanning 1981–2026.

### Delivery Behavior (`backend/delivery_behavior.py`, `frontend/src/delivery_behavior_panel.jsx`)

A cross-check layer on top of data the other tabs already persist (registered/eligible inventory, delivery notices, disaggregated CoT) — computes derived anomaly signals rather than owning new upstream fetches, except one (disaggregated CoT, described under the CoT tab above). Route: `GET /api/delivery-behavior/db?metal=XAG|XAU` (no `/refresh` — everything it reads comes from another tab's tiered refresh or from `pipeline/run.py`). Returns `{"reclassification": ..., "category_composition": ..., "deficit_context": ...}`.

- **Reclassification vs. Real Inflow** (`compute_reclassification_signal`) — the "Reclassification vs. Real Inflow" chart on the Inventory tab. Walks `inventory_aggregate`/`gold_inventory_aggregate`'s day-over-day `registered` and `total` deltas and returns **one row per real day of history**, not just candidate days — every day carries `registered_delta`/`total_delta`/`total_oz` unconditionally, so the chart shows the whole physical stack in context, not just isolated flagged days with no visible baseline.
  - **`flag_type` is bi-directional**: `"reclassification"` when registered ROSE and that day's delivery-notice volume covered less than 10% of the rise (existing eligible stock re-designated registered, not fresh metal arriving); `"deregistration"` — the mirror case — when registered FELL and delivery volume covered less than 10% of the drop (registered stock re-designated back to eligible, not metal actually leaving COMEX custody). Neither direction implies wrongdoing — both are normal, legal vault-operator status changes. A day with no delivery-notice coverage gets `flag_type: None`, same as a day with no qualifying delta — **not** the same as "checked and clean," a distinction the frontend's default "Checked period" window preserves (see coverage note below).
  - Delivery volume is `issued` alone, not `issued + stopped` (see the double-counting bug under Delivery Notices above — this is the function that bug was in). Converted from COMEX contracts to troy oz via each metal's own contract size (`backend/units.py`).
  - **Coverage note**: `delivery_notices`/`gold_delivery_notices` only have real history from **2026-02-26** onward — `inventory_aggregate` reaches back to 2020-01-02, `gold_inventory_aggregate` to 1992, so most of either metal's real history predates delivery-notice coverage and can never be flagged either way (genuinely unchecked, not confirmed clean). The chart's default window is `coverage_start_date` itself, not a fixed day count, so the default view only shows days where a flag was actually possible.
  - **Open anomaly, both metals, unresolved**: `inventory_aggregate`/`gold_inventory_aggregate` registered+eligible froze solid on 2026-03-06 (bit-for-bit identical to 2026-03-05) while that day's real delivery-notice volume was normal for both metals — not plausible as a genuine flat day. Gold additionally shows a permanent ~4.44M oz step-down in `total` starting that date that never reverses. Ruled out: a metalcharts.org site-wide outage (SHFE's inventory endpoint moved normally the same day, so whatever happened was scoped to `/api/comex/inventory` specifically). Not confirmed: whether this was a real one-time COMEX reporting gap or a metalcharts.org scraping/caching miss, and — separately for gold — why the step-down never reverses (looks like a real scope change to what `total` includes, not a stale-row artifact, since it doesn't snap back). Worth re-checking if a similar freeze/step ever recurs.

## Tab: CATCOR (Catalyst Correlation)

**Frontend**: `frontend/src/catcor_panel.jsx`. **Backend**: `backend/catcor.py`, `seed_data/catcor_events_seed.py`.

### CATCOR: what it does

CATCOR Iteration 1's event/reaction spine — answers "did this catalyst actually move the metal" with observed data only, no interpretation layer. Tracks a macro-event calendar (FOMC, CPI, NFP), sources actual/consensus values from ALFRED/ForexFactory, captures silver/gold price reactions at fixed windows (T-30min/T+5min/T+30min/T+2hr) around each event.

**Not covered here**: OFAC sanctions designations (`sanctionsTimeline-spec.md`). Despite that spec's own header nominally naming CATCOR as "owner tab," the feature's ingestion (`ofac_sanctions` source) and its display both live entirely outside this tab — a standalone **Tab: OFAC** (see below; the data was originally displayed as a Money Supply chart overlay, since removed) — and it deliberately does **not** route through this tab's Research Pane promote/dismiss/discard lifecycle, since a designation isn't a claim requiring human judgment.

### CATCOR: panel contents

Two Recharts scatter charts sharing a metal (XAG/XAU) toggle:

- **Catalyst Timeline** (top) — every captured catalyst by real calendar date, 1M/3M/6M/1Y lookback (fixed 30-day lookahead). Includes events with no known `surprise_magnitude` yet; known-future events render at reduced opacity as placeholders (never a real 0% reaction).
- **Surprise Magnitude vs. Price Reaction** (below, own T-30m/T+5m/T+30m/T+2h window toggle) — only plots events where a real `surprise_magnitude` exists.

Government-seeded events (FOMC/CPI/NFP) render as diamonds; Research-promoted (`observed`) events render as **circles** in their own amber color — event-type colored via `CATCOR_EVENT_COLORS` either way. Hovering a point in either chart doubles the size of that same event's point in the other (shared `hoveredEventId` state); clicking an `observed` point hotlinks to its originating Research session (see Tab: Research's "Research ↔ CATCOR integration" for the full mechanism — promote/demote, the hotlink wiring, and clickable legend rows all live there since they're driven by the Research tab's disposition flow, not CATCOR's own data).

### CATCOR: data flow

`main.py`'s `lifespan` runs, in order (all best-effort/independently try-excepted): `catcor.seed_events()` (loads `catcor_events_seed.py`'s static **FOMC-only** list — CPI/NFP dates used to be hand-maintained here too but reliably went stale, since nothing forced anyone back to edit the file — upserts into `event_calendar` for a 90-day-back/60-day-forward window, `event_id = f"{event_type}_{date}"` so re-seeding is idempotent; each event carries `source_tier`, currently always `"government"`) → **`catcor.seed_events_from_alfred()`** (live replacement for the old CPI/NFP lists: fetches real release dates from ALFRED's `fred/release/dates` endpoint per `ALFRED_RELEASE_ID` — `release_id=10` CPI, `release_id=50` NFP — and upserts the same row shape, own try/except so a missing `FRED_API_KEY` doesn't block the static FOMC seed above it; FOMC has no ALFRED release_id, so it's the one event type that must stay hand-maintained) → `catcor.backfill_intraday_ticks()` + `backfill_daily_closes()` (Yahoo Finance) → `fetch_and_persist_consensus()` (ForexFactory) → `fetch_and_persist_actuals()` (ALFRED) → `backfill_reactions()`.

Three core tables: `event_calendar` (event_id PK), `macro_price_reaction` (PK event_id+metal+window), `spot_price` (PK instrument+ts, **append-only** — `_fetch_and_persist_prices` writes real metalcharts.org spot ticks here; see the Price instrument registry entry under Cross-cutting data conventions for the full shape, including the now-retired separate `spot_price_snapshot` table).

**`spot_price`'s instrument families — a real collision, since fixed by `price_instruments.py`'s closed enum**: `XAG_SPOT`/`XAU_SPOT` are exclusively `main.py`'s real metalcharts.org spot ticks (60s cadence). `XAG_FUTURES_FRONT`/`XAU_FUTURES_FRONT` (`FUTURES_SERIES_ID` in `catcor.py`, aliasing `price_instruments.FUTURES_FRONT_BY_METAL`) are Yahoo SI=F/GC=F futures bars from `backfill_intraday_ticks`, a genuinely different instrument, used only for CATCOR's own event-reaction snapshot capture below. These two used to share bare `"XAG"`/`"XAU"` string keys before the instrument enum existed — futures prints running systematically ~0.3–0.6 higher than spot, interleaved on the same series, produced a real sawtooth artifact in the CoT tab's (now-removed) price chart. Existing historical rows were migrated (re-keyed by a 5-minute-grid timestamp signature — Yahoo's bars land exactly on `:00`-second, no-microsecond, 5-min-multiple timestamps with zero false positives found against the real spot series) rather than discarded.

- **ALFRED actuals**: `_fetch_alfred_change` fetches two consecutive vintage prints for `CPIAUCSL`/`PAYEMS` as of the day after `scheduled_time` and diffs them — a raw ALFRED level is NOT comparable to ForexFactory's consensus (a period-over-period change), a real bug caught during build. NFP's diff is a raw count (thousands of persons); CPI's is % m/m. `surprise_delta = actual - consensus`, recomputed whenever either value is already present regardless of fetch order.
- **Consensus**: `fetch_and_persist_consensus` matches `event_calendar` against ForexFactory's free `ff_calendar_thisweek.json` feed (title + same-instant match — "Non-Farm Employment Change" specifically, not "ADP Non-Farm Employment Change"). Only a "this calendar week" variant exists (nextweek/lastweek both 404) — consensus can only ever be captured within roughly ±6 days of "now," a permanent disclosed gap. Fetched at most once per calendar week, persisted to `forexfactory_calendar` (every entry the feed returns, every country — keyed `(week_key, title, country, event_date)`) — confirmed live that repeat hits trip a 429 and can lock out an IP entirely, so never re-fetched within the same week. This replaced an earlier flat-file cache (`runtime/forexfactory_thisweek.json`) since the file was doing double duty as a second, inconsistent persistence mechanism for data with real long-term value beyond the USD/CPI/NFP subset CATCOR actually matches. `catcor_consensus_actuals`'s `CadenceSpec(trigger="interval", interval_seconds=1800)` in `backend/sources.py` has `_schedule_loop` call it (via `_catcor_consensus_tick`) periodically alongside `fetch_and_persist_actuals`. ForexFactory's `"K"`-suffixed NFP forecasts (e.g. `"114K"`) must be scaled ÷1000 to PAYEMS's native thousands unit — a second real unit bug caught during build.
- **Snapshot capture** (`catcor.capture_snapshot`): idempotent by construction — skips if a `macro_price_reaction` row already exists for `(event_id, metal, window)`. `due_snapshots()` finds boundary-passed-but-uncaptured pairs across **every** `event_calendar` row unconditionally (no `event_type` filter — this is what lets Research-promoted `observed` events get their reactions captured automatically, with zero code changes needed for that), polled every 60s by `_schedule_loop` (via `_catcor_snapshot_tick`) under `catcor_snapshot`'s `CadenceSpec(trigger="always_on", interval_seconds=60)` in `backend/sources.py` — `always_on` is a distinct trigger value from the ordinary `"interval"` sources specifically so this source is structurally incapable of being gated by an enabled flag, since a missed window is permanent data loss unlike re-fetchable tier data. Price lookup: `db.get_spot_price_near` finds the nearest `spot_price` row **under `FUTURES_SERIES_ID`'s instruments specifically** (`XAG_FUTURES_FRONT`/`XAU_FUTURES_FRONT`, explicit as of the series-collision fix above — CATCOR's reactions were always effectively sourced from Yahoo's futures bars, not real spot ticks, this just makes that explicit rather than accidental); falls back to `settlement_price`'s `XAG_YAHOO_DAILY_CLOSE`/`XAU_YAHOO_DAILY_CLOSE` instruments — the same real daily-close series Money Supply's purchasing-power chart now reads too (per `price-architecture-spec.md`'s Fetch consolidation; these used to be two separately-fetched series, `XAG_DAILY_CLOSE` CATCOR-only vs. `XAG_CLOSE` month-end-resampled, a real bug source before the consolidation). `backfill_intraday_ticks` pulls Yahoo 5-minute bars (capped ~72 days back; 1-minute is capped at only 8 days, too short) — so ~72 of a 90-day backfill window get real intraday-precision reactions, remaining ~18 oldest days fall back to same-day daily-close approximation.
- **Routes**: `GET /api/catcor/events/db`, `GET /api/catcor/reactions/db`, `POST /api/catcor/refresh` (manual re-seed+backfill+re-fetch, `500` if `FRED_API_KEY` unset).

### CATCOR: known gaps

- 📌 `consensus_value` only populates for events within the current Sun-Sat week — events outside it keep `actual_value` but never get `surprise_magnitude`, permanent limitation of the free source, not a bug to chase.
- 📌 Intraday-precision reactions only exist for the ~72 most recent days of the 90-day backfill window.
- 📌 Iterations 2+ beyond the Research tab (FedWatch, standing watchlists, sentiment scoring) not yet built — no dedicated spec file exists yet for this; write one (per-feature convention) if/when this gets picked up.

## Tab: Research (CATCOR Research Pane, per `catcor-events-spec.md`)

**Frontend**: `frontend/src/research_panel.jsx`. **Backend**: `backend/catcor_research.py`, `backend/db.py`'s research tables, `backend/prompts/*.py`.

### Research: what it does

A workbench for working a single claim/observation by hand, one turn at a time, ending in a disposition: promote it to a tracked Catalyst Event (renders on the CATCOR timeline, see below), dismiss it as noise, or discard it outright. Supersedes the original "Iteration 2" chat MVP — nothing is auto-fetched by a model deciding it's relevant; every turn is assembled from five independently-adjustable, human-set controls (spec section 3):

1. **Model** — `forge` (amp-forge, a local Ollama-backed LAN service) or `anthropic` (Claude), chosen per turn, `forge` is always the default.
2. **Persona** — dynamically listed from `backend/prompts/*.py` (see Personas below), no registration step.
3. **Context blocks** — six checkboxes (`cot_positioning`, `comex_inventory`, `money_supply`, `market_balance`, `prior_turns`, `freeform`), each folded into the prompt only if explicitly checked.
4. **Memory mode** — `stateless` or `accumulating`; a session's current mode is stored and defaults the toggle to wherever it was left.
5. **Prompt transparency** — a live, non-editable preview of the exact assembled payload (persona text + checked context blocks' real formatted data + draft input) before sending, computed server-side via `POST /sessions/{id}/preview` (calls `assemble_prompt` directly, zero model cost) rather than approximated client-side; each turn's assembled prompt is also persisted so the transcript can show exactly what was sent, after the fact.

### Session lifecycle

Four states: `active` (editable, only status that can send turns) → `promoted` | `dismissed` (both terminal/read-only) → `discarded` (hard-deleted, never a stored status value — `research_sessions`/`research_messages` rows are actually removed, not flagged). Gating rules (`catcor_research.py`):

- **Promote** (`promote_session`) — requires a read (bullish/bearish/neutral) already set. Writes a new `event_calendar` row: `event_type="observed"`, `source_tier="discovered"`, `research_session_id` backlinking to the session, `direction` = whatever was chosen in the promote form. `consensus_value`/`actual_value`/`surprise_delta` stay `NULL` (not applicable to an Observed-origin event).
- **Dismiss** (`dismiss_session`) — requires a read, a non-empty reason, and ≥1 turn already sent (a zero-turn session has nothing to reason about — it can only be discarded). Writes a `research_log` row.
- **Discard** (`discard_session`) — no gating beyond rejecting an already-terminal session (discarding a promoted/dismissed session would orphan the `event_calendar`/`research_log` row it already produced — see Demote below for the actual "undo a promotion" path). Hard-deletes the session and its messages.
- **Demote** (`delete_promoted_event`, new) — the reverse of promote: `DELETE /api/catcor/events/{event_id}` deletes the `event_calendar` row and its `macro_price_reaction` rows, then reverts the originating session back to `active` (editable again — can be re-promoted with a corrected date/name, dismissed, or discarded). Rejects government-seeded events (`source_tier != "discovered"`) — this is only for undoing a Research promotion, never for editing AV's own seeded calendar. Surfaced in the Research tab's **session list** (not the session detail view) as a bulk action: selecting one or more `promoted` rows lights up a ⬇ header button (selecting `active` rows instead lights up a 🗑 discard button; a genuinely mixed active+promoted selection leaves both buttons visibly disabled rather than guessing which action was meant).

### Personas (`backend/prompts/*.py`)

The only contract `catcor_research.list_personas()`/`load_persona_prompt()` enforce is a module-level `PROMPT` string constant — nothing else in a persona file is read by any code (headers/docstrings are human documentation only, following an established-but-unenforced convention). Personas are listed by scanning `backend/prompts/*.py` (excluding `__init__`/`__pycache__`), so a new file is selectable immediately with no registration step. Live personas:

- `word_count_v1` — trivial word-counter, the original plumbing-validation persona, still available but no longer the hardcoded default.
- `parser_v1` — the original combined decompose+match persona, built around a `TOOL_REQUEST:` plain-text protocol for a model-driven tool-use loop. **That loop no longer exists** (superseded by the human-checked context-block design above) — left in place, unwired, importable, but selecting it will produce inert `TOOL_REQUEST:` lines nothing intercepts.
- `parser_v2` — decomposition-only (supersedes `parser_v1`'s combined job, single-responsibility split): claim text in, a numbered list of testable sub-assertions out, each tagged CHECKABLE/NOT CHECKABLE. No tool references, no matching, no verdict.
- `matcher_v1` — matching-only, the other half of `parser_v1`'s old combined job: a list of sub-assertions in, each one paired with which of the four AV data types (`cot_positioning`/`comex_inventory`/`money_supply`/`market_balance` — same names the context-block checkboxes use) would test it, or `none`. Never fetches or invents real data — naming a match is separate from actually reading that data type's current value.
- `parser_v3` — currently identical behavior to `parser_v2`; created as a documented template (every available header/option/variable spelled out, since the only real option is `PROMPT` itself) rather than a behavior change.
- `analyst_v1` — contextualizing/connecting persona from the old 2-call pipeline (takes already-matched evidence, explains historical-range context, never renders a verdict); still selectable standalone now that any persona can run on any turn.

**No persona, on either backend, has real tool-calling access** — `call_anthropic`/`call_forge` are both pure text-in/text-out (no `tools` schema sent to Anthropic's API; amp-forge's payload has no tool-schema field either). This is a deliberate architecture choice, not a Claude-vs-Ollama capability gap: AV data reaches a model exclusively via the context-block mechanism (a human checks a box, Python fetches the real data and pastes formatted text into the prompt **before** the model sees the turn) — no persona ever decides what data it gets.

### Model backend layering

`call_anthropic(system_prompt, messages, model)` / `call_forge(same signature)` — one function per vendor, identical signature and return shape (`{"final_text": str}`), pure text-in/text-out. `call_ai(backend, ...)` is a thin dispatcher between them.

- **Anthropic**: raw httpx POST to `https://api.anthropic.com/v1/messages` (no SDK, same convention as every other outbound integration in this codebase), model `claude-haiku-4-5-20251001` — Haiku specifically, not Sonnet, a deliberate cost choice since this loop is exercised interactively/repeatedly during testing (confirm the exact model string against docs.claude.com if it ever needs correcting). Requires `ANTHROPIC_API_KEY`; has no mock mode — a `mock_key` passed to `call_anthropic` raises loudly rather than silently ignoring it, since this is real, billed traffic. `_require_backend_credentials` checks the *per-request* chosen backend, not just the server-wide default, so an explicit `"anthropic"` choice against a `forge`-default server still gets a clean `500` rather than a raw `KeyError`.
- **amp-forge** (`call_forge`): one POST to a local Ollama-backed LAN service's `/chat/stream` (`FORGE_URL`, default `http://amp-forge:8001/chat/stream`; see `forge-spec.md` in the amp-dev repo for the stateless/system-prompt contract), model `qwen3:8b`, accumulates SSE `token` events. Supports a `mock_key` to skip Ollama and stream back a fixed fixture instead. The `history` field in its payload is what powers Accumulating memory mode.
- **`DEFAULT_BACKEND`**, read from `AI_BACKEND` env var, **defaults to `"forge"`** — Anthropic is an explicit opt-in for real (billed) compute.

### Context assembly (`assemble_prompt`, `catcor_research.py`)

Four of the six context blocks map to the four evidence-tool functions (`_tool_get_cot_positioning`/`_tool_get_comex_inventory`/`_tool_get_money_supply`/`_tool_get_market_balance`, unchanged from the old pipeline, still also backing `GET /api/catcor/research/evidence/db`'s zero-cost debug dump) via a new dict→labeled-text formatting layer (`_fmt_cot_positioning` etc. — this formatting step didn't exist anywhere in the codebase before this rebuild). The other two (`prior_turns`, `freeform`) have no backing tool: `prior_turns` controls whether `messages` includes session history at all, `freeform` folds in caller-supplied ad hoc text.

**The one subtle piece**: prior-turn history is included only if `memory_mode == "accumulating"` **AND** `"prior_turns"` is checked — both, not either. Stateless always wins regardless of the checkbox (spec 3.4); an unchecked box means that data is absent, full stop (spec 3.3).

### Research: data flow

`POST /api/catcor/research/sessions` → `create_session` (persists session row only) → immediately followed by `send_message` with the claim as the first turn. `send_message` now takes the full five-control signature (`backend`, `model`, `persona`, `context_blocks`, `memory_mode`, `freeform_text`, plus `system_prompt_override`/`messages_override` for the prompt-preview's per-section edit bypass) — persists the user turn immediately (with `context_blocks`/`memory_mode`/`memory_changed`/`assembled_prompt` recorded on that row) → persists the assistant turn only if the model call fully resolves (with `backend`/`model`/`persona` recorded on that row). Raises if the session isn't `active` (→ route layer returns `409`).

Routes: `POST /sessions`, `GET /sessions/db`, `GET /sessions/{id}/db` (now also returns `promoted_event` — an `event_id`/`event_name`/`scheduled_time`/`direction` object whenever `status == "promoted"`, via a new `db.get_event_for_session` reverse lookup), `POST /sessions/{id}/messages`, `POST /sessions/{id}/preview`, `POST /sessions/{id}/read`, `POST /sessions/{id}/promote`, `POST /sessions/{id}/dismiss`, `POST /sessions/{id}/discard`, `DELETE /api/catcor/events/{event_id}` (demote), `GET /personas`, `GET /evidence/db`, `GET /forge-sessions` (stub, see below).

Tables: `research_sessions` (+ `memory_mode` column, tracks the session's current setting). `research_messages` (+ `backend`/`model`/`persona` — assistant rows only — and `context_blocks`/`memory_mode`/`memory_changed`/`assembled_prompt` — user rows only; a "turn" is still a user-row/assistant-row pair, fields split across the two roles rather than duplicated). `research_log` (+ `dismiss_reason`, required non-empty). `event_calendar`'s `research_session_id`/`direction` columns are now actually written (by promote) and read (by demote, and by `list_research_sessions`'s `LEFT JOIN` which surfaces `promoted_event_id` per row for the session list's bulk-demote action) — no longer dead columns.

**amp-forge session visibility** (spec 3.4) — a known, disclosed gap: amp-forge may hold its own model-side session/context independent of what AV resends, and viewing/clearing that state has no implemented mechanism. `GET /api/catcor/research/forge-sessions` is a stub returning `{"success": false, "detail": "...not yet available..."}` rather than guessing at a wire contract that lives in a separate repo's `forge-spec.md`. `ForgeSessionsPlaceholder` (`research_panel.jsx`) is this stub's frontend surface — a collapsible panel that calls the route and shows its "not yet available" response, present so the gap is visible in the UI rather than only in this doc.

### Research ↔ CATCOR integration

A promoted session's `event_calendar` row (`event_type="observed"`) renders on the CATCOR timeline exactly like a government-seeded event, with two differences: it's a **circle**, not a diamond (government events keep the diamond shape — `makeLinkedShape`'s `diamond` param is now `type !== "observed"`), and its own palette color (`CATCOR_EVENT_COLORS.observed`, amber). Both `get_upcoming_events` and `get_event_reaction_series` (backing `/api/catcor/events/db` and `/api/catcor/reactions/db`) now select `research_session_id`/`direction`, which didn't used to be exposed at all.

Clicking an `observed` point's dot in either CATCOR chart navigates straight to the Research tab and opens that point's originating session (via `App.jsx`'s `openResearchSessionId` state, threaded down to `CatcorPanel`'s `onOpenResearchSession` and `ResearchPanel`'s `openSessionId` prop) — a government-seeded point has no `research_session_id` and is a no-op on click. Both chart tooltips show a "Click to open the research record →" hint when a point has one.

The CATCOR legend is now click-to-toggle (same convention as the CoT panel's line legend): clicking any event-type row hides/shows that type on both charts simultaneously (`hiddenTypes` state, filtered before grouping into `pointsByType`/`timelineByType`); a hidden type's legend row dims but the legend itself always shows every type regardless of what's currently plotted.

**Note on reaction capture for promoted events**: `capture_snapshot`'s nearest-tick lookup already worked generically for `observed` events with zero code changes — `due_snapshots()` queries `event_calendar` unconditionally, no `event_type` filter — so promoting a session with a recent/past `scheduled_time` gets its 4 reaction windows captured automatically on the next 60s poll, same as any CPI/FOMC/NFP event.

## Tab: Data

**Frontend**: `frontend/src/data_editorial.json` (hand-written prose/curl examples, split from the former `data_map.js` per datasources-spec.md Story #1; converted from a JS module to JSON so the test suite's sync guard can read it — `data_editorial.js` survives only as a thin re-export wrapper) + `frontend/src/data_panel.jsx`. **Backend**: `backend/sources.py` (canonical operational registry) + `backend/db.py`'s `source_health` table + `main.py`'s `/api/health/*` and `GET /api/data-sources/db` routes.

### Data: what it does

Two things layered together, since datasources-spec.md Story #1's split: a **static, hand-authored editorial map** (`data_editorial.js` — provenance prose, curl examples, per-field descriptions; not introspectable from SQLite at runtime, so this must be kept in sync by hand, see the strict Data-tab-update rule under Standing rules above), joined against **operational metadata read live from `backend/sources.py`'s registry** (`GET /api/data-sources/db` — cadence, rate limit, affinity group, `requires_env`), plus a **live Data Health view** (per dataHealth-spec.md) showing real-time fetch status per source (`GET /api/health/db`).

### Data: panel contents

`DataPanel` (outer, defaults open) fetches both `/api/health/db` (polled, on refresh) and `/api/data-sources/db` (once per mount — operational metadata doesn't change at runtime) → `TieredLoopSummary` (fast tier's enabled+interval and slow tier's enabled-only state from `GET /api/refresh/settings` — as of the per-source-cadence pass slow no longer has one shared interval to show, each source's own real cadence is on its own `SourceCard` below instead — plus healthy/total rollup per tier from `/api/health/db`'s server-derived `tier` field) → `RefreshControls` (re-mounted here as of the same pass — the actual enable/interval/force-update controls; `TieredLoopSummary` stays read-only) → one nested `<details>` per editorial entry (`SourceCard`): origin as a key-value row, then per-`sourceKeys` entry cadence/rate-limit rows (`RateLimitDisplay` — Story #6's real enforced state: a live "next eligible fetch: in N days" countdown for `min_gap_derived` sources, the raw quota for `numeric_quota` sources, an explicit "undocumented — advisory only" badge for reverse-engineered sources, never a fabricated number) and a `FetchStatusRow` (status dot computed client-side — `computeStatus`, exported from `data_panel.jsx` and shared by `App.jsx`'s `HeaderHealthDot` rather than each re-implementing the same ok/stale/error rule — against that source's `expected_interval_s`, now shipped directly on each `/api/health/db` row instead of a separate frontend-hardcoded `expectedIntervalS`; last-success time; truncated last-error text; independent "Re-run now" button hitting `POST /api/health/refresh/{source_key}` — `cot_pipeline`'s button additionally grays out inside its 7-day rate-limit window), the `curl` block in a horizontally-scrollable `<pre><code>`, then a table per SQLite table listing every field + description.

Sources with no periodic fetch of their own (`catcor_calendar`'s static seed, `research`'s on-demand chat) simply omit `sourceKeys` in `data_editorial.js` (and have no corresponding entry in `backend/sources.py`'s registry).

### Data: data flow

`source_health` (source_key PK, last_attempt_at, last_attempt_status [success|error|skipped], last_success_at, last_error, consecutive_failures — upsert, current-state only, not append-only, one row per fetch-and-persist function/loop) is infrastructure describing the health of every other tab's upstream fetch — not itself a market-data table, so it has no `data_editorial.js` SourceCard of its own.

**`backend/sources.py`** (per datasources-spec.md Stories #1+#3) is the canonical registry — replaces what used to be three separate hand-written dicts (`_FAST_TIER_REGISTRY`/`_SLOW_TIER_REGISTRY`/`_ON_DEMAND_REGISTRY`, merged into `_SOURCE_REGISTRY`) plus a module-level `_SELF_RECORDING_KEYS` set and three bespoke per-source rate-limit `if` blocks. Every source is one `SourceDefinition` (key, label, `affinity_group`, `fetch_fn`, `tables`, `cadence: CadenceSpec`, `rate_limit: RateLimitSpec`, `requires_env`, `self_recording`), registered into `sources.SOURCE_REGISTRY` from `main.py` once every fetch function it references exists as a real name (same ordering constraint the old registries had). `CadenceSpec.trigger` is one of `"interval"` (fired by the generic scheduler on a fixed cadence, subject to `enabled_flag`), `"always_on"` (fired unconditionally, no `enabled_flag` branch ever consulted — CATCOR's `catcor_snapshot` reaction-capture source uses this specifically because a missed window is permanent data loss, unlike every re-fetchable source), or `"manual_only"` (reachable only via `POST /api/health/refresh/{source_key}`, plus once at boot if `fire_at_startup=True`). `fire_at_startup` (a separate, orthogonal field, not a fourth trigger value) fires a source once, ~1s after boot, in addition to whatever its `trigger` otherwise does — `catcor_startup` (`trigger="interval", fire_at_startup=True, interval_seconds=604800` — the former `_catcor_startup` one-shot chain, also re-running weekly) is the canonical example. `money_supply`/`metals_prices`/`lbma_fix`/`census_trade`/`treasury_outlays`/`treasury_outlays_by_agency` were originally `trigger="manual_only", fire_at_startup=True` (fire once at boot, never again automatically) — as of the per-source-cadence pass, all six are now `trigger="interval"` with a real recurring cadence too (see the Standing rules' Tiered background refresh bullet for the per-source numbers), so `manual_only` is no longer used by any currently-registered source except `cot_pipeline` (which has its own `gate_on="persisted_data_age"` self-gating, a different mechanism — see below). A distinct fourth `"startup"` trigger value existed briefly during the initial registry build (dispatched by hand-written `asyncio.create_task(...)` calls in `lifespan`, outside the generic scheduler entirely — a third, separate dispatch pattern) and was folded into `fire_at_startup` shortly after, once it became clear that pattern was hiding a real bug: `money_supply`/`metals_prices` were labeled `trigger="startup"` but had no corresponding `lifespan` call, so they never actually fired automatically until this fold fixed it. A single `_schedule_loop()` in `main.py` (ticking every 1s, dispatching per-source on its own `CadenceSpec`) now handles every source uniformly, including the former startup-only ones — replacing the old `_fast_tier_loop`/`_slow_tier_loop`/`_event_tier_loop`/`_consensus_tier_loop` four-loops-by-era pattern and the separate `lifespan`-level startup task-creation calls alike. `POST /api/refresh/force` and the one-shot startup refresh still call `_refresh_fast_tier`/`_refresh_slow_tier` directly, now reading `sources.sources_by_tier("fast"/"slow")` instead of the old dicts, so they can't drift from what `_schedule_loop` itself fires.

`GET /api/health/db` remains a thin read of `source_health` plus two fields derived at read time from the matching `SourceDefinition`, never stored: `expected_interval_s` (from `CadenceSpec.expected_interval_s`, the property `2 × this` staleness threshold is computed against) and `tier` (a small scheduling-only label — `"fast"|"slow"|"always-on"|"interval"|"on-demand"`, deliberately distinct from `affinity_group`'s four-value source-category grouping, so `TieredLoopSummary`'s existing fast/slow rollup keeps working unchanged). The route still does not compute ok/stale/error itself — the frontend computes status client-side against the shipped `expected_interval_s`.

**Per-source configurable intervals**: `POST /api/data-sources/{source_key}/interval` (`{"interval_seconds": int}`) lets any `trigger="interval"` source's cadence be overridden independently — originally built when all slow-tier sources shared one blanket `_refresh_settings["slow_interval_s"]` value; as of the per-source-cadence pass every interval-triggered source already owns its own real `interval_seconds` (see the Standing rules' Tiered background refresh bullet), so this override mechanism now serves hand-tuning a specific source away from its own already-real default (e.g. wanting `silver_leverage` more frequent than its shared 25h peers), not compensating for a shared value that was wrong for most sources. Overrides live in a mutable `_interval_overrides: dict[str, int]` side-table in `main.py`, checked by `_schedule_loop` *before* falling back to a source's own registered `cadence.interval_seconds` — deliberately not a mutation of `CadenceSpec`/`SourceDefinition` themselves, which stay genuinely frozen (their immutability is what makes cadence auditable by construction, per `sources.py`'s own docstring). Persisted in the `interval_overrides` table (`backend/db.py`, `source_key TEXT PRIMARY KEY, interval_seconds INTEGER`) — seeded into `_interval_overrides` once at boot — so a deliberate per-source tuning choice survives a restart, same durability `ui_settings.refresh_enabled` now also has for the master enable flag (see Standing rules above — previously the tier-wide toggle was the one setting that reset on restart; that gap is closed too). The route rejects `always_on` sources (protects `catcor_snapshot` — never overridable into a skippable/slower cadence) and `manual_only` sources (nothing to override — no recurring timer exists; as of the per-source-cadence pass this means only `cot_pipeline`). `GET /api/data-sources/db` overlays any live override onto its `cadence.interval_seconds`/`expected_interval_s` fields before serializing, so the frontend's existing read picks up an override for free. `frontend/src/data_panel.jsx`'s `SourceCard` renders one `IntervalEditControl` per `sourceKey` (not per card — same established per-`sourceKey` granularity its cadence/rate-limit rows already use) inside each `trigger="interval"` row.

A small always-visible header dot (`HeaderHealthDot` in `App.jsx`) polls `/api/health/db` every 60s independent of which tab is active — red if any tracked source is erroring, yellow if any is stale with no errors, green otherwise; links nowhere, since the Data tab nav button is already one click away for drill-down.

### Census International Trade (`census_trade`, per international-trade-spec.md)

Documented here in the Data tab; its frontend surface is the Inventory tab's **Trade Flow** panel (see Tab: Inventory — added after the spec's original v1 backend-only scope). U.S. Census Bureau International Trade API, monthly imports/exports for HS 7106 (silver) and HS 7108 (gold, comparison-only per the standing "gold as context" rule — no gold-specific signal or panel). Answers "where does US silver supply actually come from, and is that mix shifting" with a primary-source view of trade flow (value, quantity, country-of-origin/destination) — does not attempt to reproduce USGS's net-import-reliance %, which needs domestic mine-production data AV doesn't track.

`census_trade` table (`metal`, `flow`, `hs_code`, `cty_code`, `cty_name`, `year`, `month`, `value_general_usd`, `value_consumption_usd`, `qty`, `qty_unit`, `fetched_at`; PK `(metal, flow, hs_code, cty_code, year, month)`) — **upsert, not append-only** (`INSERT ... ON CONFLICT DO UPDATE`, same shape as `settlement_price`), since Census revises trade data annually every April, unlike CFTC's immutable-once-published reports.

**Confirmed live** (real `CENSUS_API_KEY`, both flows, both metals, several months, including a real production run): field names are `GEN_VAL_MO`/`CON_VAL_MO` (imports) and `ALL_VAL_MO` (exports) for value, `GEN_QY1_MO`/`CON_QY1_MO` (imports) vs. the differently-named `QTY_1_MO` (exports) for quantity, sharing `UNIT_QY1` for the unit code. **Census reports no quantity/weight at all for HS 7106 or HS 7108** — the qty fields are always `"0"` and `UNIT_QY1` is always `"-"` (Census's own not-applicable sentinel), consistently across every row checked. `qty`/`qty_unit` persist as `NULL` accordingly; this is a schema-level upstream gap, not a per-row data hole, and not something to build oz-conversion logic against.

**Also confirmed live, a real correction mid-build**: Census's true publication lag is **~2 months, not ~1** — both the current calendar month and the immediately-prior one return HTTP `204` (empty body, not an error status) until released. `_fetch_and_persist_census_trade` treats `204`/empty-body responses as "not yet published, skip this month" and fetches a wider window (`CENSUS_TRADE_MONTHS_PER_FETCH + 2` months back) so 3 real months still land per run. This lag also broke the originally-spec'd rate-limit gate design: gating on "is the latest **persisted** `(year, month)` under 25 days old" (mirroring `_refresh_cot_pipeline`'s CFTC pattern, where report age closely tracks fetch recency) is never true in practice for Census, since by the time a new month is available the previous latest month is already 2+ months old — the gate would never actually skip. `_refresh_census_trade` instead gates on **wall-clock time since the last fetch attempt** (`source_health.last_attempt_at`, via a new `db.get_source_health(source_key)` single-row read), which correctly approximates "don't re-check Census more than once per ~25 days" regardless of publication lag.

`_refresh_census_trade` (`main.py`) wraps `_fetch_and_persist_census_trade` with that gate — skips (records `last_attempt_status="skipped"`) if the last fetch attempt is under ~25 days old, otherwise fetches and records its own success, since its `SourceDefinition.self_recording=True` (alongside `cot_pipeline`) in `backend/sources.py`. Cadence: as of the per-source-cadence pass, `CadenceSpec(trigger="interval", interval_seconds=604800, fire_at_startup=True, min_gap=timedelta(days=25), gate_on="last_attempt_at")` — a real weekly scheduler tick (converted from the earlier `manual_only`/fire-once-per-restart design) plus manual force-refresh via the Data tab's "Re-run now" button. The `min_gap`/`gate_on` fields no longer control *whether the scheduler fires* (only `interval_seconds` does, for any `trigger="interval"` source — `_schedule_loop` never reads `min_gap`), but `_refresh_census_trade`'s own internal gate check still enforces the true ~25-day floor regardless of how often the scheduler ticks — most weekly ticks record a cheap "skipped" attempt, not a real fetch. `min_gap`/`gate_on` stay on the `CadenceSpec` purely so `expected_interval_s` and the Data tab's rate-limit display still reflect the real 25-day cadence rather than the more-frequent scheduler-check interval. Silently skips at startup if `CENSUS_API_KEY` isn't set, same as LBMA. `GET /api/census-trade/db?metal=&flow=&hs_code=` is the sole read route — no live `/refresh` route, per the same "a government monthly release isn't something a page load should trigger" reasoning as CoT. `GET /api/health/db` enriches `census_trade`'s row with `last_period` (via `db.get_latest_census_trade_period()`), same convention as `cot_pipeline`'s `last_report_date`.

**`implied_qty_oz`** — since Census reports no real quantity for these HS codes (see above), `db.get_census_trade` computes an estimated ounce figure per row **at read time, never stored** (per the computed-at-read-time convention): `value_general_usd ÷` that month's `XAG_YAHOO_DAILY_CLOSE`/`XAU_YAHOO_DAILY_CLOSE` month-end close (resampled at read time via `db.get_settlement_price_by_month`, see the Price instrument registry entry under Cross-cutting data conventions). It's explicitly an estimate — a monthly value total divided by a single month-end price, not a reported weight — `NULL` whenever that month's spot close is missing, and the Trade Flow panel renders it with an "(est.)" qualifier accordingly.

- 📌 `census_trade`'s `qty`/`qty_unit` are confirmed-live always `NULL` — Census does not report a quantity/weight figure for HS 7106 or HS 7108 today. Not a bug; revisit only if Census ever starts populating `UNIT_QY1` for these codes.
- 📌 HS 7112 (scrap) and other Critical Minerals List comparators (e.g. copper 7402/7403) are deferred to a documented Phase 2, not discarded. (`census_trade`'s original "no frontend panel" v1 scope is closed — the Inventory tab's Trade Flow panel is its frontend now.)

## Tab: Stack

### Stack: what it does

Per `specs/stackTracker-spec.md`, then **deliberately regressed to a minimal surface at the user's explicit request** ("just a spot to aggregate count and price data," building toward "I have 7 2013 Maples, 6 2014 Maples" — see Regression note below): a personal CRUD inventory of physical silver/gold holdings. Joins against AV's live spot price for melt valuation. **Is not** a pricing authority for numismatic value, not synced/hosted/aggregated anywhere, not a filesystem the user manages.

**Storage is physically separate from `argentvigil.db`, structurally not just conventionally**: a dedicated `runtime/stack.db` (own `DB_PATH`, own `get_conn()`/`init_db()` in `backend/stack_db.py`, mirroring `backend/db.py`'s conventions) plus `runtime/stack_images/{stack_item_id}/{uuid}.{ext}` for photos — never `ATTACH`ed to `argentvigil.db`. Cost basis, numismatic notes, and photos of a real physical stack are the one category of AV data that should never end up in a shared/demo-able database, per the spec's own rationale. The only cross-read is melt valuation pulling live spot prices from `argentvigil.db` via a direct Python import of `backend.db.get_latest_spot_prices()` — a read, not a write, so persist-on-fetch is unaffected. `backend/stack_db.py`'s DDL is a wholly separate string from `backend/db.py`'s `DDL`, so `tests/test_conventions.py`'s table-ownership scan (which only scans `db_module.DDL`) never needs a `NON_SOURCE_TABLES` entry for these tables — confirmed by a dedicated assertion in `tests/test_stack.py`.

**No `backend/sources.py` registration, no `data_editorial.json` card** — Stack Tracker has no upstream fetch at all (it's pure user CRUD), the same exemption `research_sessions`/`squeeze_case_log` already have from the Data-tab registry/editorial convention.

### Regression to a minimal surface (2026-08)

The originally-built richer form (weight-per-item split by metal, numismatic grading block, photos, reference links, a separate bulk-add form) was real and worked, but the user explicitly asked to strip the Add flow back to **date, quantity, price paid, series** — with the stated end goal of eventually seeing "I have 7 2013 Maples, 6 2014 Maples" as a grouped breakdown, not a flat undifferentiated list. Per the user's own resolution: **the richer backend stays fully live, just hidden** — `stack_tracker.jsx`'s Add form only surfaces the minimal fields; photos/reference-links/numismatic-grading fields are still real, still work, just tucked under each item's "Advanced" collapsible in the detail view rather than front-and-center. Nothing was deleted from the schema or backend logic — this was a UI/entry-flow simplification, not a feature removal.

**A real gap this left behind, since fixed**: the first cut of "Advanced" was read-only display only (a summary sentence — "Mint year: 2013. Graded PCGS MS70...") with photos/links as the only actually-editable pieces inside it — there was no way to *set* `mint_year`/`grading_service`/`grade`/`certification_number`/`numismatic_value`/`numismatic_value_as_of`/`numismatic_notes` through the UI at all except via bulk-update or the old removed form, confirmed live when the user asked "why isn't there a date field for any of these" about `numismatic_value_as_of` specifically. Fixed by turning "Advanced" into a real editable sub-form (its own `<form onSubmit={handleSave}>`, same `handleSave` function the main form uses, own "Save numismatic details" button) covering all seven fields — kept as a separate `<form>` from the main one rather than merged into it, since Photos/Reference-links inside the same Advanced section each already have their own nested `<form>` for upload/add-link, and HTML forbids nesting `<form>` elements.

**A second gap in the same area, caught by a direct spec review (2026-08) and fixed in the same pass**: that seven-field editable form still missed `mint_mark`/`mintage` — spec §3's numismatic block, backend round-trip already correct, just no input anywhere (they'd been lumped in with the genuinely-still-dormant `premium_paid`/`silver_weight_oz`/`gold_weight_oz` in `handleSave`'s pass-through comment, an inconsistent grouping rather than a deliberate cut, since every other §3 field got a real input). Added both as plain text/number inputs alongside mint year. **Also found in the same review**: the item-detail header showed Total oz/Melt value/Gain-loss but never the raw `numismatic_value` or `numismatic_premium` figures — both already computed and returned by the API (`compute_valuation`), just never rendered — despite spec §6.1's explicit "melt, numismatic, and total as three distinct numbers" requirement. Fixed by adding both to the header, shown only when `numismatic_value` is actually set (nulls-over-zeros — no point showing a `—`/`—` pair for pure bullion).

**The split-form gap fully closed (2026-08)**: the "minimal main form + separate Advanced numismatic sub-form" structure was itself the underlying gap — several columns (`premium_paid`, `silver_weight_oz`, `gold_weight_oz`, `form`) had no input anywhere in either form, only ever pass-through-preserved on save. Per the user's explicit "I want to be able to see and edit all the fields used" request, `ItemDetail` was rebuilt into **one comprehensive form covering every `stack_items` column**, organized into labeled sections (Basics / Weight / Numismatic) rather than a flat wall of inputs, but genuinely one `<form onSubmit={handleSave}>` with one Save action — the two-form split is gone. `METALS_FULL` (`silver`/`gold`/`bimetallic`) is used here instead of the simplified Add form's `METALS` (`silver`/`gold` only), since this editor is meant to cover the dormant bimetallic path too. Photos and Reference Links remain their own sibling `<details>` sections with independent-action sub-forms (upload, add-link) — unchanged, since HTML still forbids nesting `<form>` elements and each already had its own save action distinct from the main field-editor's Save.

**`unit_weight_oz` — the real mechanism behind "AV does the math."** The user's stated habit was manually computing a total ("I have 14 silver quarters, which is 2.5312 oz") and typing the pre-computed total into a weight field — exactly the kind of manufactured-number risk the nulls-over-zeros convention exists to avoid elsewhere. Resolved by adding `unit_weight_oz` (oz per single unit — 1oz coin, 10oz bar, 0.1808oz for a 90%-silver junk-silver quarter) as the primary weight input; `total_weight_oz` (and everything downstream — melt value, gain/loss) is computed server-side as `unit_weight_oz × count`, never hand-entered. The frontend offers a quick-pick (1 oz / 10 oz / 90% silver quarter / Custom) mirroring `stack.UNIT_WEIGHT_QUICK_PICKS`. The dormant per-item `silver_weight_oz`/`gold_weight_oz` fields (the original richer model, including bimetallic support) still exist and still work if directly set — `stack._total_weight_oz` prefers them over `unit_weight_oz` when both happen to be present, so nothing built on top of the old fields silently broke.

### Schema

- **`stack_items`**: `description`, `metal` [silver/gold — `bimetallic` accepted, only offered in the full item editor's metal picker, not the simplified Add form's], `form` [coin/bar/round/other, editable in the full item editor], `unit_weight_oz` (the primary weight input — oz per single unit, see above), `silver_weight_oz`/`gold_weight_oz` (the dormant explicit-per-item-weight path — wins over `unit_weight_oz` if set, editable in the full item editor's Weight section), `count`, `lot_id`, `purchase_date`, `purchase_price`, `premium_paid` (editable in the full item editor), `series` (see below) plus a nullable numismatic block (`mint_year`, `mint_mark`, `mintage`, `grading_service`, `grade`, `certification_number`, `numismatic_value`, `numismatic_value_as_of`, `numismatic_notes`). Every one of these columns is now editable somewhere — the Add form still only surfaces description/series/metal/unit-weight/quantity/date/price for quick entry, but the full item editor (see below) covers everything.
- **`stack_reference_links`**: one-to-many, `stack_item_id` FK, `url`/`label`/`added_at` — its own collapsible section on the item editor page.
- **`stack_item_images`**: one-to-many, `stack_item_id` FK, `file_path` (relative path under `stack_images/`), `caption`, `added_at` — its own collapsible section on the item editor page.

**Nulls over zeros throughout** — a missing spot price leaves that leg of melt value `null`, never a stale-fallback or manufactured `0`; an item with no `series` groups by its own `description` instead (see Series below), never silently dropped from the grouped view.

### Series (sovereign-coin identification — freehand text, not a validated enum)

`stack.SERIES` — American Eagle / Canadian Maple Leaf / Austrian Philharmonic / British Britannia / South African Krugerrand / Australian Kangaroo-Kookaburra / Mexican Libertad / Chinese Silver Panda / Ukraine Archangel Michael / Niue / APMEX / US - Constitutional / Other-Generic — a list of **quick-pick suggestions only**, not a server-validated allowlist (APMEX is a dealer, "US - Constitutional" covers 90%-silver junk coinage generally rather than one sovereign mint issue — both added anyway per the same "this DB is mine" freehand precedent as Luxor/Niue). The junk-silver quarter unit-weight quick-pick (0.1808oz) already existed for this material; "US - Constitutional" as a series lets it also be tagged/grouped consistently rather than defaulting to no series. `series` is a plain `TEXT` column and any non-empty string is accepted; there's no 400 for an unrecognized value. **Deliberately made freehand at the user's explicit request** ("this DB is mine... why not make the series 'Luxor'" — a casino chip, not a sovereign coin) after an earlier pass had validated it as a closed enum; that validation is gone. `frontend/src/stack_tracker.jsx`'s `SeriesInput` component (shared across Add/Edit/Bulk-update) renders `SERIES` as one-click `<select>` options plus a `Custom…` entry that reveals a free-text field — the dropdown is a convenience, the underlying value is just text. **This column used to be `country_of_origin`** — repurposed via a guarded `ALTER TABLE ... RENAME COLUMN` in `stack_db.init_db()` (idempotent, no-op on a fresh DB); old country values ("Canada," "Niue," ...) were preserved verbatim under the new column name on migration, not auto-mapped into the series list at the time — since the column is unvalidated now, those migrated values are just as usable as any other freehand entry.

### Group update (`POST /api/stack/items/bulk-update`)

Select any set of rows (checkboxes on `ItemList`, which renders identically in both the flat list and a group's drilldown — so selection works from either) and apply a **field subset** to all of them at once, e.g. tagging all 12 rows from a single order as "2013 Canadian Maple Leaf, PCGS MS70" in one action. `stack.BULK_UPDATE_FIELDS` covers **every `stack_items` column except `count` and `lot_id`** (expanded from an original narrower set — `series`/`mint_year`/`numismatic_notes`/`purchase_price`/`purchase_date` only — to the full column set at the user's explicit request, "I should be able to bulk update any one (or all) of the nested fields of the coin"). `count` stays excluded since it's inherent to how a row was created (single vs. bulk-entry), not a "what these items share" fact; `lot_id` stays excluded since it's system-managed (assigned by `create_bulk`, never user-editable). `metal`/`form`/`grading_service` carry the same allowlist validation here as `create_item`/`update_item` (`_validate_item_fields`'s rules, duplicated inline in `bulk_update_items` since they need to run only when those specific keys are present in a given bulk update, not unconditionally) — a bad value can't silently corrupt every selected row.

**Only fields actually present with a non-empty value in the request are applied** — an omitted or blank field is left untouched on every target row, never blanked out. This is a real semantic difference from `PUT /items/{id}` (a full replace) and is why `bulk_update_items` doesn't just loop `update_item` per id. The frontend's `BulkUpdateForm` starts every field blank (not pre-filled from any selected item) — per the user's own call, so a field you don't touch can never accidentally overwrite real per-row data with an empty value. `BulkUpdateForm`'s own field set mirrors `ItemDetail`'s full item editor (see below) minus `count`/`lot_id`, sectioned the same way (Basics / Weight & Value / Numismatic).

### Portfolio summary strip

`SummaryStrip` (`stack_tracker.jsx`), sitting above the list/group view: **Total spent → Unrealized gain/loss → Current value → Held** (in that order, per the user's explicit reorder request — a first cut had Current value ahead of Gain/loss). `Held` shows both metals' oz totals plus each metal's `silver_gain_pct`/`gold_gain_pct` inline (see the DCA/gain-% conventions above). All four read from `GET /api/stack/summary/db` unchanged — this was a pure display-order fix, no backend change.

### Grouped views (default: by series; also by date — the "7 2013 Maples" goal)

**Default view on opening the tab is Grouped by series** (`mode` state defaults to `"series"` — changed from an earlier "default by date" pass at the user's explicit request) — every series' entries start collapsed into one row showing just count/oz/melt-value/spent; clicking a row drills into its member rows. A three-way toggle (`GROUP_MODES` in `stack_tracker.jsx`: Grouped by date / Grouped by series / Flat list) switches modes.

Both grouped modes share one backend shape and one frontend component:
- `GET /api/stack/date-summary/db` (`stack.date_summary`) groups every item by `purchase_date` (items with no date fall into one shared "Unknown date" bucket, not one bucket per `None`, so they're still visible rather than silently missing), sorted **newest-first**.
- `GET /api/stack/series-summary/db` (`stack.series_summary`) groups by `series` (falling back to `description` for un-seriesed items, so bars/generic rounds still group sensibly).
- Both return the same per-group shape via a shared `stack._summarize_group` helper: `item_count`, `total_count` (sum of `count` — real physical quantity), `total_weight_oz`, `total_melt_value`, `total_spent`, `item_ids` (for drilldown) — nulls-over-zeros throughout (a group with no real melt_value anywhere in it reports `null`, not a fabricated `0`).
- `stack_tracker.jsx`'s `GroupList` component renders either group type identically — a `comex-table` row per group (not cards; cards were tried first and dropped at the user's request), columns `Group / Total oz / Melt value` (`Qty` was dropped entirely per the user's call that "Total oz" already covers it; `Spent` was later dropped too per the same "keep melt value and total ounces" request, once the summary strip above already surfaces total spend at the portfolio level). The flat `ItemList` keeps its own `Date / Series-description / Total oz / Price paid / Melt value / Gain-loss` shape (Price paid stays here since it's the per-row figure, distinct from the group-level rollup GroupList shows). Both tables' oz cells render via `fmtOzBare` (bare number, no repeated "oz" unit — the column header already says it), reserving `fmtOz` (with the unit suffix) for standalone summary/header figures that aren't under a labeled column, e.g. the "Held" summary line and the item-detail header. Both tables also carry `.comex-table--zebra` (alternating row background, index.css — scoped to this modifier class so other tabs' tables are unaffected) per the user's explicit request. Clicking a group row drills into that group's member rows via `ItemList`; clicking an individual item row (in the flat list or inside a drilldown) opens the full item editor (see below).

**Every column in both `GroupList` and `ItemList` is sortable** — a shared `useSort` hook (click-to-toggle-ascending-then-descending, arrow indicator on the active column via `SortTh`) rather than a per-table bespoke implementation. `null`/`undefined` values always sort to the end regardless of direction, so a group/item with a missing figure (e.g. no live spot for melt value) never jumps to the top of a descending sort just because it compares as falsy. `GroupList` defaults to `label` ascending; `ItemList` defaults to `purchase_date` descending (most recent first, matching the app's existing "newest first" convention elsewhere).

**Both tables cap to ~10 visible rows and scroll vertically past that**, per the user's explicit request, applying uniformly across all three list views (Flat, Grouped by date, Grouped by series all render through one of these two components — no per-view special-casing needed). A new CSS class, `.comex-table-wrap--capped` (`index.css`, layered onto the existing shared `.comex-table-wrap` rather than replacing it, so this stays Stack-specific and doesn't affect every other tab's tables), sets `max-height: 364px; overflow-y: auto` and pins the header row (`position: sticky; top: 0`) with a background matching the real page body color (`#0f1117`) so scrolled rows don't visually bleed through the sticky header. The 364px figure is a visual ~10-row estimate (`.comex-table td`'s real padding/line-height), not an exact row-count guarantee for content that wraps taller than one line.

### DCA (dollar-cost-average) strip

Sits **between the list and the Charts pane** (per the user's explicit placement request), rendered by `DcaStrip`/`DcaLine` in `stack_tracker.jsx`. Two separate `comex-panel` boxes side by side — **silver left-justified, gold right-justified** (`justifyContent: "space-between"`, per the user's explicit layout request; a first cut put both metals in one shared box and was corrected) — each showing one inline line (label, DCA, spot, all on the same line — an even earlier cut stacked label/value/spot vertically per metal and was also corrected). `total spent on that metal ÷ total real oz held of that metal` (`stack.portfolio_summary`'s `silver_dca`/`gold_dca`, computed the same way as the existing per-metal `silver_gain_pct`/`gold_gain_pct` — spend and oz both accumulated independently per metal in one pass over `list_items()`, `NULL` if either side has no real data). Rendered large/bold (`fontSize: 22`) relative to the rest of the panel, per the user's "make the DCA more prominent" request. Shows both the DCA figure and live spot inline (`(spot $63.56/oz)`) — the DCA figure alone is the one deliberately colored. A metal with no DCA (e.g. no gold purchases in the current filter) simply doesn't render its box — never an empty box with nothing in it.

**Color is inverted from the rest of this panel's convention, on purpose**: green when **DCA > spot** (your average cost is above today's price — you're currently underwater, which per the user's own framing is the *actionable, favorable* read for someone still accumulating: "when my DCA is higher than spot, I need to be buying"), red when **DCA < spot** (your stack is already cheaper than today's price — nothing urgent to do). This is the opposite of the "Held" summary line's gain/loss coloring (green = currently profitable there) and the opposite of this app's standing green=favorable/red=unfavorable convention elsewhere — a real, deliberate exception for this one panel, not an inconsistency to "fix" later.

`portfolio_summary`'s response also carries `spot_silver`/`spot_gold` (the same live prices `_spot_prices()` already reads) — backs the color comparison and is rendered directly.

**Reacts to the pie-chart legend click below it** (see Charts → cross-chart filtering) — when a series is selected, `DcaStrip` recomputes both metals' DCA from only that series' items (`dcaForMetal`, a client-side twin of the backend's spend÷oz math run over a filtered subset rather than `list_items()`), and each box's label gains a `(Series Name)` suffix so it's unambiguous which scope is showing.

### Charts (`stack_tracker.jsx`'s `StackCharts`, Recharts — same library/theme as every other AV tab)

A collapsible "Charts" pane, default open, sitting **below the group/flat list** in the list view (moved there from above the list at the user's explicit request — the list itself is the primary content, charts are a supplementary view of the same data, not the first thing seen on open). Three charts (a fourth, cumulative-spend-only line, was built and then removed at the user's request as redundant with the gap chart below):

- **Stack by series (pie, oz-weighted)** — one slice per series with a real oz total, reusing `palette.js`'s `VAULT_COLORS` (the same categorical palette every other AV pie already uses, for cross-tab consistency). **No chart title** (removed at the user's request — the "Charts" pane summary already frames it, and the legend below names every slice). Brought up to this app's UI standard (`frontend/docs/UI_STANDARDS.md`'s Legends section) after a review pass — the original build had only a static legend and no chart-side interaction, which the standards doc calls out as incomplete: **clicking a legend row now highlights that slice** (`clickedSeries` state) — dims the other slices (`fillOpacity: 0.35`), gives the clicked slice a light outline (`#e8ecf4` stroke, 3px vs. the base 2px), and the legend button itself gets `legend-btn-row--baseline` styling, mirroring `comex_inventory.jsx`'s existing vault-pie click-highlight pattern rather than inventing a new one. Direct percent labels on each slice (`pieSliceLabel`, suppressed below 4% to avoid label clutter on the long tail of small series) satisfy the dataviz skill's requirement that this palette's CVD-adjacent-pair floor only ships with a secondary encoding — color alone was never the sole identity channel. Each slice also carries a 2px stroke in the app's own surface color (`#141820`) as the "surface gap" separator between touching slices, per the dataviz skill's mark-anatomy spec — the original build had only `paddingAngle={1}` with no explicit ring.
  - **Pinnable, cross-chart** (added in a later pass, per the user's "adjust when clicking a spot on the [growth] chart" request): the pie defaults to the *live* series composition (from `series_summary`) but switches to an **as-of-date** composition when a date is pinned on the oz-growth chart below (see next bullet) — `seriesCompositionAsOf(items, pinnedDate)` in `stack_tracker.jsx`, computed client-side by filtering the already-fetched `items` list to `purchase_date <= pinnedDate` and regrouping by `series` (falling back to `description`, mirroring `stack.series_summary`'s own grouping rule so the live and pinned views group identically). No dedicated backend route — the frontend already holds the full item list, so this is a pure client-side recompute, same reasoning as the metal-filter's `filterGroups`. **Color assignment is keyed off the live series list, not the pinned subset** — a series pinned-out-of-view (not yet purchased as of that date) simply doesn't get a color computed, but a series that *is* present keeps the same color it has in the live view, rather than slices repainting into different colors depending on how many series happen to be present at a given pinned date.
  - **Legend click cross-filters DCA and both charts below it** (per the user's explicit "clicking American Eagle, I'd see the graphs below change as if focused only on rows with series American Eagle" request) — `clickedSeries` state, **lifted from `StackCharts` up to `StackTracker`** (a real restructuring, not just a new prop) specifically so `DcaStrip` — a sibling of `StackCharts`, not a child — can react to the same click. `timeseriesFromItems(items)` in `stack_tracker.jsx` is a client-side twin of `stack.timeseries()`'s cumulative-spend/oz/melt-value math, run over `items.filter(...)` scoped to the clicked series' rows rather than the whole portfolio, reusing each item's own already-server-computed `melt_value`/`total_weight_oz` (from `list_items_with_valuation`) rather than re-deriving from spot — the frontend has no direct spot-price access outside what `/items/db` already returned. Both the oz-growth and gap charts read from this same `activeTimeseries` (either the portfolio-wide `/timeseries/db` response or the filtered client-side recompute), so neither chart needed its own separate filtering logic once `activeTimeseries` existed as one shared value. Clicking the same legend row again clears `clickedSeries` and all three panels (DCA, oz-growth, gap) revert to portfolio-wide.
- **Cumulative oz held over time** (two lines, silver and gold separately — added per the user's explicit "I want a line for stack count in ounces over time" request, plus their call that silver/gold shouldn't be combined into one misleading number) — reads `cumulative_silver_oz`/`cumulative_gold_oz` off `activeTimeseries` (portfolio-wide by default, or the series-filtered recompute — see the pie bullet above). **This chart is the pin origin** — clicking a point (`onClick` on the `LineChart`, `handleOzChartClick` reading Recharts' `activeLabel`) sets `pinnedDate`, which both the pie above and this chart itself react to (a `ReferenceLine` marks the pinned x-position here); clicking the same date again un-pins. A "clear" link appears above the pie whenever a date is pinned, and the tooltip's title reminds the reader the chart is clickable ("(click to pin)"). Pinning a date and clicking a series are independent, composable filters — both can be active at once.
- **Cost basis vs. current value gap** (area, replaces an earlier two-crossing-lines design the user disliked) — plots `cumulative_melt_value − cumulative_spend` from that same `activeTimeseries` as a single area, shaded green above zero and red below via one **split SVG gradient** (`stackGapFill`/`stackGapStroke`, both with a `zeroOffset` stop computed from the real min/max of the data — where the y=0 crossing actually falls in the rendered domain), rather than the reader having to compare two separate lines to judge over/under. A `ReferenceLine` at y=0 marks the baseline explicitly. Directly answers "am I up or down, and by how much" — the same underlying comparison the two-line version made, in a form that doesn't require mentally subtracting two lines to read it. An on-chart note states that "current value" uses **today's live spot** applied to the running oz total as of each date, not a historical price (AV doesn't track deep historical spot for this purpose, and manufacturing one would violate the standing nulls-over-zeros/never-fabricate-a-reading convention) — so the chart isn't misread as a price-history chart. Not click-to-pin (only the oz-growth chart originates a pin) — no competing gesture conflict, it just doesn't need one since it's not the chart the pinned-pie feature was requested against.

`GET /api/stack/timeseries/db` (`stack.timeseries`) — one row per real `purchase_date` (items with no date are excluded entirely, not bucketed, since there's no real position for them on a time axis), chronological, each row carrying `day_spend`, `cumulative_spend`, `cumulative_silver_oz`, `cumulative_gold_oz`, `cumulative_melt_value` (`NULL` if no spot price is available for either metal, same nulls-over-zeros convention as every other valuation figure — never a fabricated `0`). Computed at read time from `list_items()` + `_spot_prices()`, nothing persisted. The gap chart's `gap = cumulative_melt_value - cumulative_spend` is computed client-side from this same response (or its series-filtered `timeseriesFromItems` twin), not a separate backend field.

**Metal filter** (`All metals` / `Silver` / `Gold` dropdown, `metalFilter` state) applies to whichever mode is currently active — for Flat list it filters `items` directly; for the grouped modes it filters each group's `item_ids` down to the visible metal and drops any group left with zero members, so a filtered group's displayed aggregate reflects only what's actually shown (never the unfiltered total sitting next to filtered rows).

**Not year-level yet, by design** — "7 2013 Maples, 6 2014 Maples" needs grouping by `(series, mint_year)`, not just `series`; `mint_year` already exists on the schema (dormant, under "Advanced" in the detail view) but the grouping key doesn't use it yet. Flagged as the next real step once the user is ready for it — see Known gaps.

### Cost basis: `count` vs. bulk entry (two distinct creation paths, unchanged by the regression)

A single row's `purchase_price` is **total-for-that-row's own `count`** — e.g. one row with `count: 3` for 3 identical, not-individually-tracked items has `purchase_price` as the total for all 3, via the plain `POST /api/stack/items` path.

**Bulk entry** (`POST /api/stack/items/bulk`, `stack.create_bulk`) is for "I bought 7 of these, but want to track each one individually." Given `{quantity: 7, unit_price: 32.50, ...shared fields}`, it creates **7 fully independent rows**, each `count=1`, each `purchase_price=32.50` (per-unit, not lot-total), all sharing one generated `lot_id` (a plain UUID tag, not a FK). Deleting or editing one row never touches its lot-mates. **The simplified frontend folds this into one Add form** — `AddForm` posts to `/api/stack/items` when `quantity <= 1`, `/api/stack/items/bulk` otherwise, dividing the entered total price by quantity to get `create_bulk`'s expected per-unit price — there is no longer a separate "Bulk add" screen the user has to navigate to.

### Valuation (computed at read time, never persisted — `backend/stack.py`)

- `total_weight_oz = unit_weight_oz × count` (primary path) or `silver_weight_oz × count` / `gold_weight_oz × count` (dormant explicit-weight path, wins if set) — `stack._total_weight_oz`.
- `melt_value = total_weight_oz × spot price for that item's metal`, `NULL` (not `0`, not a stale fallback) if the metal's live spot price is unavailable — `stack.compute_valuation`.
- `numismatic_premium = numismatic_value − melt_value`, only computed when `numismatic_value` is set.
- `unrealized_gain = (melt_value + coalesce(numismatic_value, 0)) − purchase_price`, both $ and %.
- `GET /api/stack/summary/db` (`stack.portfolio_summary`) rolls the above up across every row: total spent, total current value, total unrealized gain/loss, total oz held by metal, value split by metal, **and per-metal gain %** (`silver_gain_pct`/`gold_gain_pct` — that metal's live melt value vs. what was actually spent on that metal specifically, `NULL` if nothing's been spent in that metal yet). Powers the "Held" summary line's `299.575 oz Ag (-22.0%) / 8.0 oz Au (-11.0%)` annotation — deliberately per-metal, not the combined portfolio gain %, since a silver-heavy loss shouldn't be diluted by an unrelated gold gain or vice versa.

### Photos (still fully live, just under "Advanced" in the detail view)

Upload via `<input type="file" multiple accept="image/*">` → `POST /api/stack/items/{id}/photos` (multipart, `python-multipart` in `requirements.txt`) → backend generates a UUID filename, writes to `runtime/stack_images/{item_id}/`, inserts the `stack_item_images` row. **Enforced caps**: 5 photos/item, 10MB/photo (`stack.MAX_PHOTOS_PER_ITEM`, `stack.MAX_PHOTO_BYTES`), rejected server-side with a 400. Served back via a dedicated `StaticFiles` mount at `/stack_images` (`main.py`) — the frontend renders `<img src="/stack_images/{item_id}/{uuid}.ext">` directly, no signed URLs. **The dev-server Vite proxy needed its own `/stack_images` entry** (`frontend/vite.config.js`) — it only forwarded `/api/*` to the backend originally, so in dev (port 5173) an `<img>` pointed at `/stack_images/...` 404'd against Vite's own dev server instead of reaching the backend; a real bug caught live (uploads were succeeding, just invisible). Deleting a photo removes both the DB row and the file on disk; deleting an item cascades to all its photos' files and rows, plus its reference links.

### Routes (`backend/main.py`, all under `/api/stack/`)

`GET /items/db` (list with computed valuation), `GET /items/{id}/db` (detail + images + reference_links), `GET /summary/db` (portfolio rollup), `GET /series-summary/db` (grouped-by-series rollup), `GET /date-summary/db` (grouped-by-date rollup, default view), `GET /timeseries/db` (cumulative spend/oz/melt-value by purchase date, powers the Charts pane), `POST /items` (single-item create), `POST /items/bulk` (bulk-entry expansion), `POST /items/bulk-update` (group update — focused field subset applied to a caller-selected set of ids, see above), `PUT /items/{id}` (update), `DELETE /items/{id}` (delete, cascades), `POST /items/{id}/photos` (multipart upload), `DELETE /photos/{id}`, `POST /items/{id}/links`, `DELETE /links/{id}`.

Only the `GET .../db` routes are `/db`-suffixed reads; the mutating routes are plain user CRUD with no upstream to guard against, so they're covered by a `"/api/stack/"` entry in `tests/test_conventions.py`'s `ALLOWED_NON_DB_API` rather than the persist-on-fetch `/db` convention.

### Seed data loader (`utils/load_stack_seed.py`, one-off tooling)

Not app code — a one-time script (per the `utils/` convention for human-run diagnostics/one-offs) that loaded the user's real historical holdings from `seed_data/agStack.csv`/`auStack.csv` (date, count, price-per-unit, total columns) into `stack.db` via the same `stack.create_item`/`create_bulk` paths the app itself uses, not raw SQL — so every seeded row went through the same validation a real Add would. Defaults to a dry run (prints row counts); `--commit` actually writes. Handled real data quirks found in the source CSVs: missing years (assumed 2026), a tab-delimited row, a fractional "count" that was actually an oz quantity (the user's constitutional/junk-silver pile — loaded as `count=1, unit_weight_oz=3.575`), and one row that looked like "140 units" but was actually 14×10oz bars — corrected before loading, confirmed against the user directly rather than guessed. Cross-checked its own output against each CSV row's stated total (`count × price_per_unit`) before committing, and the final loaded totals were independently re-verified against a hand-computed sum of the raw CSV outside the loader's own logic. Not intended to run again against different data without review — a one-time historical backfill, same category as `utils/backfill_census_trade.py`.

### A real deployment bug worth remembering: code changes need a running-process restart

Twice during this feature's build, a route or proxy change was correct in source but **the running `vigil.sh`-managed backend/frontend processes were still serving the pre-change code** — confirmed live both times (a fresh `POST /api/stack/items` 405'd until `vigil.sh restart backend`; photo `<img>` tags 404'd until the Vite dev server picked up its new proxy config). The test suite validates the code in-process via pytest, which re-imports fresh on every run — it does **not** touch the long-running dev-server processes at all, so a green test suite is not evidence the running app has the change. **Always restart the relevant `vigil.sh`-managed process(es) after a backend or vite-config change, before treating a fix as done** — this isn't unique to Stack Tracker, but it's the tab where it was caught.

### A real cross-tab bug the Stack tab's addition exposed: `_VALID_NAV_SECTIONS`

`main.py`'s pinned-default-tab feature (see Standing architectural rules above) has its own hardcoded allowlist, `_VALID_NAV_SECTIONS`, separate from `App.jsx`'s `SECTIONS` array — the two are supposed to stay in lockstep by hand, and they didn't: Stack was added to `SECTIONS` (giving it a working nav button and, per the pinned-tab feature's own doc claim, "automatic" pin support) but never added to `_VALID_NAV_SECTIONS`, so `POST /api/ui/pinned-section {"section":"stack"}` 400'd — confirmed live, and silently swallowed by the frontend (`togglePin` in `App.jsx` doesn't surface a failed POST), so pinning the Stack tab visibly did nothing with no error anywhere. Fixed by adding `"stack"` to `_VALID_NAV_SECTIONS`; regression-tested in `tests/test_stack.py`'s `test_stack_tab_is_pinnable`. **No mechanical guard exists for these two lists staying in sync** (unlike the registry↔editorial sync `test_conventions.py` already enforces for the Data tab) — worth building one if a tab ever gets added again without noticing this the same way.

- 📌 **Year-level grouping not built yet** — the user's actual end goal ("7 2013 Maples, 6 2014 Maples") needs `series_summary` to group by `(series, mint_year)` instead of `series` alone. `mint_year` already exists on the schema; only the grouping key needs to change. ### Entity detail (2026-08-26 follow-up)

Three new child tables capture it:

- **`ofac_aliases`** — every alias per entity (A.K.A./F.K.A./N.K.A./primary "Name"), not just the one `entity_name` was assembled from. Confirmed live at ~45,500 rows across the full dataset.
- **`ofac_addresses`** — confirmed live this is a genuinely **separate top-level XML section** (`Locations`), not nested under the party the way vessel `Feature` detail is. Reached via `Profile`'s own `Feature`/`FeatureVersion`/`VersionLocation` (`FeatureTypeID=25`) pointing at a `Location`'s `@ID`. **A real join-element bug caught and fixed during implementation**: the first attempt guessed the connecting element was `FeatureVersionReference` (a real element name in this schema, but attached the other direction — on `Location`, pointing back at the `FeatureVersion` that cited it) — using it would have silently resolved zero addresses. The real element, confirmed by tracing one real entity end-to-end (`Feature ID=150025`/`FeatureVersion ID=200025`/`VersionLocation LocationID=25` → real `Location 25`, Havana, Cuba), is `VersionLocation`. Address parts are typed (`LocPartTypeID` → `ADDRESS1`/`ADDRESS2`/`ADDRESS3`/`CITY`/`STATE/PROVINCE`/`POSTAL CODE`, a `ReferenceValueSets` lookup) rather than fixed field names; country resolves via a separate `CountryID` → `CountryValues` join. Confirmed live at ~23,500 rows — most partial (country-only is common; ~14,500 have a real `address1`, ~17,200 a real `city`), real street-level addresses confirmed for e.g. a London/Zurich/Madrid/Tokyo/Panama City multinational entity.
- **`ofac_id_documents`** — confirmed live (**correcting a wrong assumption made during planning**, before any code was written against it) that the primary join is **direct**: `IDRegDocument` is itself a top-level XML section (22,667 real elements in a full SDN pull) where each document carries its own `IdentityID` attribute pointing straight at a `Profile/Identity/@ID` — NOT primarily reached via `Location`, though a smaller, real `Location`-mediated path also exists (183 `IDRegDocumentReference` instances) and is captured the same way since every `IDRegDocument` carries `IdentityID` regardless of which path references it. `id_type` resolves via `IDRegDocTypeValues` (Passport, SSN, Cedula No., Driver's License No., etc.); `issuing_country` via the same `CountryValues` join addresses use. Confirmed live at ~23,400 rows, including real passport numbers with issuing country.

**Replace-all, not append-only, not diffed row-by-row** (`db.replace_ofac_entity_detail`) — every daily fetch deletes and re-inserts all three tables' rows for every `ofac_uid` present in that day's pull. Deliberately simpler than a per-child diff: these represent OFAC's current claim about an entity, the same way `entity_name`/`program_tags` do on the parent row, not a history of when an alias was added. This was an explicit design discussion with the user (not assumed) — a "secondary staging tables + row-by-row ETL diff" alternative was raised and rejected: it would duplicate the existing set-arithmetic diff logic against a second SQL table instead of an in-memory list, for no benefit given there's exactly one consumer and no expensive transform to stage.

**Read route**: `GET /api/ofac/{ofac_uid}/db` — the parent designation plus all three child arrays, 404 if the uid doesn't exist. `sanctions_panel.jsx`'s `entity_name` cell is clickable, fetching this route on demand (not prefetched for all ~19,700 rows) and rendering aliases/addresses/ID documents in a detail view; nulls-over-zeros throughout (an entity with no captured address, for instance, shows nothing fabricated in its place).

**Same database, deliberately** — a "should OFAC get its own SQLite file, like Stack Tracker's `stack.db`?" question came up in the same conversation and was resolved against splitting: Stack's split is a **data-sensitivity** argument (cost basis/numismatic notes/photos of the user's real physical holdings, explicitly "never end up in a shared/demo-able database" per that tab's own spec) — OFAC is public government data, the opposite case. Keeping it in `argentvigil.db` means any future cross-check against price/CoT/money-supply data (if ever wanted again, after the chart-overlay idea was dropped) is a plain SQL join, not an `ATTACH` or a cross-service call.

One `comex-panel` (non-collapsible — the whole tab is this one view, no sub-panels to nest), header row carries a `ChartStaleness` badge (`sourceKey="ofac_sanctions"`) showing fetch health + row count, same convention every other tab's data-backed sub-panel uses.

Widened from an `entity_name`-only match in a 2026-08-27 follow-up, per the user's explicit "search by any top-level field" request — they chose one unified box over a per-field input row (the simpler of two options offered).

  - **Default view, per the user's explicit 2026-08-29 request**: `groupBy` defaults to `"program"` (not `"none"`), and `GroupTable` defaults to sorting by its own `latest_date` field descending — together, opening the tab shows programs most-recently-touched first. `latest_date` is the MAX `chart_date` across a group's own member designations, computed client-side in `groupRows` from data already fetched (no new backend field) — the same real `chart_date` (`COALESCE(designation_date, first_seen_snapshot_date)`) the flat table already sorts by. - **Row display**: Date / Entity (vessel rows append `(flag, type)` inline, e.g. "TIFON (Cuba, Tug)") / Type / Programs (comma-joined) / **Legal Basis** (2026-08-27 follow-up — see below) / List, plus Delisted when "Include delisted" is checked.

### Legal basis (2026-08-27 follow-up)

The user asked whether there's "detail behind the programs" beyond the bare code string, wanting to link into it if so. Investigated live: OFAC's Advanced XML has no standalone per-program reference/description page, and the formal `LegalBasis`→`SanctionsProgram` link in the XML's own reference dictionaries is **confirmed broken** — every `LegalBasis` element's `SanctionsProgramID` attribute points at `SanctionsProgramID=1` ("Unknown"), regardless of what program it's actually the legal authority for. There is, however, a real, mostly-populated substitute: the same `EntryEvent` (`EntryEventTypeID=1`, "Created") that `designation_date` already comes from carries its own `LegalBasisID`, resolving via a `LegalBasisValues` lookup to a real human-readable string — e.g. `RUSSIA-EO14024` designations resolve to `"Executive Order 14024 (Russia)"`, `SDGT` to `"Executive Order 13224 (Terrorism)"`. Confirmed live against a full real fetch: **18,031 of 19,707 rows (91.5%)** resolve to something real; the remainder resolve to the dictionary's own "Unknown" placeholder and are persisted as `NULL`, never the literal string, per nulls-over-zeros.

New `ofac_designations.legal_basis` column, parsed in `_ofac_parse_sanctions_entries` (extended to accept a `legal_basis_values` lookup built in `_ofac_parse_reference_dicts` alongside the existing `country_values`/`locpart_types`/`id_doc_types`), tracked on the SAME earliest-`EntryEvent`-wins basis `designation_date` already uses (they come from the same element, so whichever `EntryEvent` supplies the kept date also supplies the kept legal basis). Backfilled on re-seen entities the same way `designation_date`/`entity_name`/`program_tags`/`vessel_flag`/`vessel_type` already are (persisted `NULL` → a real value from today's pull, never the reverse) — `diff_and_persist_ofac_designations`' existing backfill branch, one more field, no new mechanism. This is per-*designation* context, not a per-*program* reference — a program code still has no single canonical "what does IRAN mean" page to link to, since OFAC's own data doesn't have one either.

### OFAC: data flow

Single `GET /api/ofac/db` fetch on mount (no window/date-range param — the full dataset is small enough, confirmed live at ~19,700 rows, ~a few hundred KB of JSON, to filter/sort/paginate entirely client-side rather than adding server-side pagination). No `/refresh` route on this tab — same "the frontend never triggers a live upstream fetch" persist-on-fetch rule every other tab follows; `ofac_sanctions` refreshes on its own daily slow-tier cadence regardless of whether this tab is ever opened. `GET /api/ofac/{ofac_uid}/db` (entity-detail follow-up) is fetched on demand per clicked row, not prefetched.

## Conventions

- **Backend**: stdlib `sqlite3` (no ORM), `httpx.AsyncClient` for outbound calls (one shared client via FastAPI lifespan), routes are thin — fetch, reshape, upsert, return `{"success": bool, "data": ...}`. HTTP errors from upstream become `HTTPException(502, str(e))`.
- **Pipeline**: intentionally stdlib-only, no third-party deps — keep it that way. Config constants belong in `pipeline/config.py`, not scattered inline.
- **Frontend**: React 19 + Vite 5 + Recharts, no state library, no router (single page, tab-like sections via `App.jsx`). Chart colors come from `palette.js`, not ad hoc hex values.
- **Units**: COMEX figures are troy oz; SHFE is kg natively, converted via `1 kg = 32.1507 oz` (constant appears in both `main.py` and any frontend display — keep consistent). COMEX open interest contracts are 5,000 oz each.
- **AV Voice Rules** (standing rule, applies repo-wide to any user-facing copy — formerly documented in the retired `SPEC.MD`, now stated here as the canonical source): no "alarming"/"critical" framing on deficit trends, always show the ±20% uncertainty qualifier on above-ground stock figures, label runway/track-record figures explicitly as historical description or context — never as prediction.
- **Collapsible sections**: the established UI pattern for any collapsible pane is native `<details className="collapsible-pane"><summary className="collapsible-pane-title">…</summary><div className="collapsible-pane-body">…</div></details>` (CSS in `index.css`) — nest freely. Prefer this over a `useState` show/hide toggle unless more complex interaction state is needed.
- **Custom legends over Recharts' built-in `<Legend>`**: chart legends in this codebase are hand-rolled (`.comex-legend-list`/`.comex-legend-item`/`.comex-legend-swatch` classes). See `frontend/docs/UI_STANDARDS.md` for the fuller standard this has converged on (horizontal layout, click-not-hover for detail, clicking a legend row must also highlight that series on the chart, always show every relevant item regardless of current value) — check new interactive legends/tooltips against that doc rather than inventing a new pattern per chart.
- **Custom scatter-point shapes for cross-chart consistency**: CATCOR's two charts and its legend all use the same diamond shape per event type (`.comex-legend-swatch--diamond` for the legend; a shared `makeLinkedShape` renderer for the charts themselves).

## Tests

`tests/` — pytest + respx + pytest-asyncio, listed in the single `requirements.txt` alongside the runtime deps (a separate `requirements-dev.txt` was tried and dropped at the user's call — nothing here deploys anywhere needing a runtime/dev split, and one file means `vigil.sh`'s bootstrap installs everything, so a fresh clone can run the suite immediately; `pytest.ini` sets `testpaths=tests` + `asyncio_mode=auto`). Run with **`bash utils/vigil.sh test`** (pytest args pass through — `vigil.sh test -k leverage`, `vigil.sh test tests/test_routes.py`; `test backend`/`test all` are accepted no-op aliases for start/stop muscle memory, `test frontend` prints an honest "no frontend tests exist" notice) or `.venv/bin/python -m pytest -q` directly — the full suite is 83 tests in **under 10 seconds**, cheap enough to run on every change; that speed is a design requirement (the suite exists partly to replace ad-hoc curl checks, which only works if running it costs nothing). Built 2026-07-20 to (a) guard regressions mined from this doc's own confirmed-bug narratives, (b) give a mechanical verification path, and (c) keep the Cross-cutting data conventions section enforced, not aspirational. **`test_lifespan_integration.py` (added 2026-07-25) is the one file that doesn't run in milliseconds** — its two real `asyncio.sleep` waits (letting `_schedule_loop` complete at least one real tick pass before asserting) account for essentially all of the suite's ~8s runtime; every other file is still sub-second. The "under half a second" framing from this section's original build is retired accordingly — 8-ish seconds is still cheap enough to run on every change, just no longer the original number.

**Ground rules, enforced by construction in `tests/conftest.py`**:

- **Never touches `runtime/argentvigil.db`** — the `tmp_db` fixture monkeypatches `db.DB_PATH` to a throwaway file and runs `init_db()`, so DB tests exercise the real SQLite DDL/SQL, not mocks.
- **Never calls a live upstream** — all outbound httpx is intercepted by respx with synthetic real-shaped fixtures (`tests/helpers.py`). Deliberate on two axes: speed, and a fast suite hitting real upstreams would violate the diagnostic-pacing rule (Development Notes) and burn quotas — the GoldAPI lesson.
- **Never runs `lifespan`** — the `client` fixture drives the app through `httpx.ASGITransport` (the same httpx the app itself uses; starlette's `TestClient` shim was tried first and dropped — its import fires a `StarletteDeprecationWarning` under the installed starlette, and a suite that ships warning-free matters more than the shim's convenience), so no startup fetch chain or scheduler loop fires; the `upstream_client` fixture hands `backend.main._client` a real `AsyncClient` for respx to intercept when a fetch function itself is under test.
- **`date.today()`-driven logic is frozen** with `helpers.make_fake_date` monkeypatched over `backend.main.date` — the weekend spot-skip, LBMA walk-back, census month windows, and curve-spread candidate sweeps are all deterministic regardless of when the suite runs.

## Running it

```bash
bash utils/vigil.sh start         # everything, as background daemons (venv bootstrap + backend :8000 + frontend :5173)
bash utils/vigil.sh restart backend   # after backend Python edits — picks up the change (no --reload running)
bash utils/vigil.sh stop          # stop everything
python3 pipeline/run.py           # CoT pipeline only, no server needed
bash utils/vigil.sh test          # full test suite (83 tests, ~8s) — see ## Tests; pytest args pass through
```

Run the pipeline at least once before the frontend, since the CoT tab reads from `/api/cot/db`, which reads `cot_silver`/`cot_gold` from `runtime/argentvigil.db` — empty tables make that route return a `500` ("No CoT data persisted yet. Run pipeline/run.py first.").

The exchange-inventory/FRED/spot-price data populates itself on first backend startup regardless (a one-time unconditional refresh runs in `main.py`'s `lifespan`) — the tiered background refresh only *repeats* on a schedule if explicitly enabled via `POST /api/refresh/settings` or forced via `POST /api/refresh/force`. CATCOR's event calendar and reaction backfill also run automatically on every startup — no manual trigger needed, though `/api/catcor/refresh` exists for an on-demand re-run. ALFRED calls need `FRED_API_KEY` set in whatever shell launches the backend — without it, the event calendar and price reactions still populate, but `actual_value`/`surprise_delta` stay `NULL`. Research's Anthropic backend needs `ANTHROPIC_API_KEY` only if `AI_BACKEND=anthropic` is explicitly set (default is `forge`, which needs no key but does need the `amp-forge` LAN service reachable). The LBMA fix (see Silver/Gold sections above) needs `GAPI_API_KEY` (GoldAPI.io, free tier) — without it, the `lbma_fix` source's fetch_fn logs a skip message and the rest of the app boots normally; the `XAG_LBMA`/`XAU_LBMA` settlement_price instruments just stay empty (no frontend consumer currently surfaces them anyway, see the Silver/Gold sections above).

**Always run Python through `.venv`, never bare `python3`.** `bash utils/vigil.sh start` creates
`.venv` on first run and installs `requirements.txt` into it (`fastapi`, `uvicorn`, `httpx`,
`python-dotenv` — none of these are on system Python). Before running any Python command
against this repo — import checks, one-off scripts, `python -c "..."` sanity tests — run
`source .venv/bin/activate` first, or invoke `.venv/bin/python` directly. `pipeline/` is the one
exception: it's intentionally stdlib-only by design and *can* run under bare `python3`, but
`main.py`/`db.py`/anything importing `fastapi`, `httpx`, or `dotenv` cannot.

## Development Notes

Standing instructions for every interaction in this repo — distinct from each tab's "known gaps" (which describe upstream/data limitations, not workflow). Add to this section directly as new quirks/preferences come up.

- **Always run Python through `.venv`, never bare `python3`** — see the full rule under "Running it" above. `pipeline/` is the sole stdlib-only exception.
- **Use `utils/vigil.sh` to stop/start services** — always allowed, no need to ask first.
- **Bump the version number in this file's title (`# ArgentVigil vX.Y.Z`) on every feature completion** — a new spec, or any change bigger than a typo/doc tweak. Not on every edit; only when a development effort actually completes. **`README.md`'s title carries the same version and must be bumped in the same change** — `tests/test_conventions.py`'s `test_readme_version_matches_claude_md` fails the suite on drift (deliberately not a per-commit auto-increment, which would make the number meaningless against this rule's "feature completion, not every edit" semantics). A versioned pre-commit hook (`utils/githooks/pre-commit`, wired via `git config core.hooksPath utils/githooks` — per-clone, one-time; already set in this clone) runs the full suite on every commit, so drift can't be committed either; it resolves the repo root via `git rev-parse --show-toplevel`, works from any cwd, and fails with a bootstrap hint if `.venv` is missing. README structure (as of v1.27.0): three fixed top sections — BUSINESS LEVEL / TECH LEVEL / NEXT UP — plus orientation-only `backend/README.md` and `frontend/README.md`; all three stay high-level and point here for the exhaustive record, never duplicate this doc's narratives.
- **`utils/` scripts other than `vigil.sh` are human-facing diagnostics/one-offs** (`claims/claimExtract.py`, the metalcharts sniffers, etc.) — not app code. ## Coding Modes

Two modes govern how work in this repo is done. **Learning mode is the default** — only switch to auto mode when explicitly told to.

### Learning mode (default)

- **Never validate UI changes yourself** — no headless browser, no automated screenshotting. The user is at the screen and will look; acknowledge their eyes are better than a headless check for this.
- **Pause after delivering any "demo-able" change** for an interactive walkthrough — explain/demo it, be ready to defend the approach or change it. The user always makes the final call.
- **The goal is learning** — everything AV touches, from physical vault volumes to how the AI pieces work, not just shipping the change.
- **Ask rather than guess** when something is ambiguous.

### Auto mode (explicit opt-in only)

- **Maximize work done before stopping.**
- **Ask no questions** — if a decision is unavoidable, pick the option that would have been recommended anyway.
- **Guess rather than ask.**
